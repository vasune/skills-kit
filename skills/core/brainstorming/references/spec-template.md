# Шаблон спеки

Спека — это согласованный restate, который пережил сессию. Пишется в репозиторий проекта (`SPEC.md` в корне или `docs/spec-<тема>.md`) и коммитится. Порог — работа дороже ~2 часов, несколько файлов или решение, которое жалко потерять. Ниже — полный набор разделов; сокращать можно, выбрасывать «Границы» и «Критерии успеха» — нельзя.

## 1. Цель и пользователь

- **Цель одной фразой:** что человек сможет делать, а не что мы построим.
- **Пользователь:** кто именно, в каком сценарии, как часто.
- **Почему сейчас:** что изменилось и почему не через год.
- **Не входит (non-goals):** что сознательно не делаем и почему. Самая полезная часть: половина расхождений — молчаливое несогласие о том, чего в работе нет.

## 2. Команды

Точные команды, которыми спека проверяется на исполнение. Одна команда — один результат; команда изменилась — меняется спека.

```bash
# установка зависимостей
...
# запуск для проверки вручную
...
# тесты
...
# сборка
...
```

## 3. Структура

Куда что ложится: дерево каталогов и файлов, которые появятся или изменятся. По одному пояснению на строку — зачем этот файл существует.

```text
src/
  feature/        логика фичи
  feature/api.*   вход для интерфейса
tests/            проверки, которые докажут успех
```

## 4. Стиль: один реальный пример

Не описание правил, а фрагмент кода из этого проекта, на который нужно равняться: имена, обработка ошибок, формат ответа. Стиль, описанный словами, каждый понимает по-своему.

```python
# реальный фрагмент из проекта — не псевдокод
```

## 5. Тесты

- **Уровень:** что проверяется юнит-тестом, что интеграционным, что сквозным сценарием.
- **Главный сценарий:** один тест, который докажет, что фича работает, — его имя и команда.
- **Края:** пустой ввод, ошибка внешнего сервиса, граница диапазона.
- **Как проверяется, что тест ловит поломку:** тест обязан падать без правки и проходить с ней.

## 6. Требования (EARS)

Каждое функциональное требование — одной формулой, а не абзацем: видно триггер, субъект и проверяемое поведение. Пять паттернов покрывают почти всё; формула одна — `Когда <триггер>, система должна <поведение>` и её варианты:

| Тип | Формула | Пример |
|---|---|---|
| Всегда | Система должна <поведение>. | Система должна возвращать JSON на любой `/api/*`. |
| По событию | Когда <триггер>, система должна <поведение>. | Когда в запросе нет токена, система должна вернуть 401. |
| По состоянию | Пока <состояние>, система должна <поведение>. | Пока идёт импорт, система должна отклонять повторный запуск. |
| Условное | Пока <состояние>, когда <триггер>, система должна <поведение>. | Пока пользователь админ, когда он удаляет запись, система должна писать аудит-строку. |
| Опциональное | Если включено <свойство>, система должна <поведение>. | Если включён кэш, система должна хранить ответ 60 секунд. |

Три примера под наш контекст:

- Когда пользователь открывает отчёт без фильтра, система должна показать данные за последние 30 дней.
- Когда внешний API отвечает ошибкой, система должна вернуть 502 и записать причину в лог, не отдавая тело ответа наружу.
- Пока идёт пересчёт, система должна показывать прогресс и не принимать вторую задачу.

Требование без наблюдаемого результата — не требование: «быстро» и «удобно» переформулируются в критерий успеха с числом (§10). Требования нумеруются (`R-1`, `R-2`), чтобы тест и коммит могли на них ссылаться.

## 7. Сценарии приёмки (Given/When/Then)

2–3 сценария на фичу: главный путь, отказ и граница. Формат даёт тесту скелет, а человеку — проверяемое обещание (в английской литературе — Given/When/Then, у нас «Дано/Когда/Тогда»).

```text
### AC-1: <название сценария>
Дано <предусловие: состояние системы или данные>
Когда <одно действие>
Тогда <наблюдаемый результат: что видно, что в ответе, что в БД>
```

- Один сценарий — одно решение. Если в «Тогда» два несвязанных результата, это два сценария.
- Отказ обязателен: что видит человек при неверном вводе, недоступном сервисе, отсутствии прав.
- Сценарий, который нельзя проверить запуском или взглядом в интерфейс, — пожелание, а не приёмка.

## 8. Ошибки и края

Таблица, а не проза: по строке на каждый реальный отказ. Отсюда берутся тесты на края (§5) и сообщения интерфейса.

| Сценарий | Ожидаемое поведение | Код / сообщение |
|---|---|---|
| Пустой или неполный ввод | отказ до записи, поле подсвечено | 422, «Заполните …» |
| Неверный формат (дата, число, email) | отказ с указанием поля | 422, «Неверный формат …» |
| Нет прав на объект | доступ закрыт, без раскрытия существования объекта | 403 |
| Внешний сервис недоступен или таймаут | повтор по политике, затем честная ошибка | 502, «Сервис недоступен, попробуйте позже» |
| Повторный запуск той же операции | идемпотентно: тот же результат, без дубля | 200/409 по решению спеки |

## 9. Границы: что можно без спроса

| Уровень | Что входит | Поведение агента |
|---|---|---|
| Always | локальные правки в границах спеки, тесты, форматирование | делать молча |
| Ask | новые зависимости, изменения схемы данных, публичные интерфейсы | спросить до работы |
| Never | ослабление тестов и проверок, секреты в репозитории, удаление чужих изменений | не делать |

## 11. Допущения и как их проверить

2–5 допущений, на которых держится спека. У каждого — тип (откуда взялось) и способ проверки: запрос, замер, тест или разговор с человеком. Допущение без проверки — вера; проверяется оно первым.

| Допущение | Тип | Как проверить | Когда |
|---|---|---|---|
| ... | сказал / выведено из кода / по умолчанию индустрии / неясно | ... | до кода / после первого среза |

Тип задаёт поведение: «сказал» и «выведено из кода» можно принимать в работу, но «выведено» помечается в спеке и перепроверяется при первом противоречии; «по умолчанию индустрии» — самое слабое, его проверяют до первого среза; **«неясно» блокирует реализацию** — сначала вопрос человеку, потом код.
