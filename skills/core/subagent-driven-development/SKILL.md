# Исполнение плана через субагентов

План из мелких задач исполняется циклом: свежий субагент на задачу → две приёмки → коммит → следующая задача. Родитель не пишет код, а брифит, проверяет и коммитит; длинная сессия с одним агентом так не масштабируется.

## Когда открывать

- Есть утверждённый план (`plan`) с задачами по 2–5 минут.
- Фича из 5+ задач или из нескольких независимых частей.
- План заканчивается фразой «исполнять через subagent-driven-development».
- Не для 1–2 задач: родитель сделает их сам быстрее, чем напишет брифы.
- Не для механической работы без рассуждений — это скрипт, а не субагент.

## Цикл

1. **Реестр задач из плана.** `[ ]` / `[x]` по каждой; в работе ровно одна (или несколько независимых — см. ниже). Отмечать после приёмки, а не после отчёта ребёнка.
2. **Бриф на одну задачу** — по `delegating-to-subagents`: текст задачи из плана дословно, путь репозитория и ветки, файлы, которые можно менять, команда приёмки, запреты. Свежий субагент, без истории диалога.
3. **Приёмка 1 — соответствие спеке.** Прочитать дифф и сравнить с текстом задачи: сделано ровно то, ничего лишнего, ничего не забыто. Отчёт ребёнка — самоотчёт, доказательство — дерево и дифф.
4. **Приёмка 2 — качество.** `requesting-code-review`: статический скан, baseline-тесты, независимый ревьюер. Для документации и текстов — `verification-before-completion` и вычитка против источника.
5. **Правки.** Дефекты — корректировка курса тому же ребёнку или отдельный fix-агент с точным списком; максимум два цикла, дальше родитель чинит сам. Не «перезапустить и попробовать ещё раз».
6. **Коммит** — родитель, по путям, по `git-naming`. Ребёнок не коммитит и не пушит.
7. **Следующая задача** — только после двух зелёных приёмок и коммита.

## Параллельно или последовательно

- **Параллельно** — только независимые задачи с непересекающимися файлами: одна пачка параллельных задач, общие гейты после всей пачки (см. `delegating-to-subagents`).
- **Последовательно** — всё, что меняет общий контракт, схему данных, форму экспорта или общий файл. Два потока, переименовывающих одно и то же, по отдельности зелёные, а вместе красные.
- **Изоляция** — по желанию: каждому ребёнку свой `git worktree` (`git-worktrees`), тогда основное дерево остаётся чистым для следующей задачи.

## Что остаётся родителю

- Архитектурные решения и развилки плана.
- Формулировки, которые увидит человек (тексты интерфейса, отчёты, письма).
- Финальная приёмка и коммит.
- Решение по честному блокеру: если ребёнок доказал, что план неверен, — вернуться к человеку, а не молча перепланировать.

## Стоп-условия

- Задача провалилась дважды — разбираться самому, третий перезапуск не помогает.
- План противоречит коду или среде — остановиться и сказать человеку, а не «подогнать» план по ходу.
- Ребёнок нашёл дефект в соседней задаче — записать в реестр, не чинить «заодно» вне очереди.

## Грабли

- **Принять отчёт за результат.** «Все тесты зелёные» из отчёта не заменяет собственный прогон и чтение диффа.
- **Запустить следующую задачу до коммита предыдущей.** Дерево смешивается, и уже не понять, чья правка сломала тест.
- **Дать ребёнку весь план вместо одной задачи.** Он сделает «заодно» соседнее — это ровно то, что цикл должен исключить.
- **Параллелить задачи, которые пишут в один файл** — конфликт и потерянная работа.
- **Забыть обновить реестр.** «Сколько сделано» отвечается по реестру, а не по памяти о разговоре.

## Связанное

- `plan` — откуда берётся реестр задач.
- `delegating-to-subagents` — механика брифа, параллельности и приёмки.
- `requesting-code-review` — вторая приёмка.
- `verification-before-completion` — доказательство вместо отчёта.
- `git-worktrees` — изоляция потоков.
