# Разбор ТЗ заказчика перед разработкой

## When to Use

Пришло ТЗ, спека или «задание на разработку» нового сервиса, и его надо разобрать до кода:
понять суть, найти дырки, оценить сроки, собрать вопросы заказчику. Не для написания плана
по уже понятной задаче (навык `plan`) и не для извлечения обязательств из документов.

## Порядок

1. **Открыть markdown-версию, а не docx.** Если в архиве `.md` + `.docx` + `.pdf`, это почти всегда
   один документ: проверить это кодом (распаковать `word/document.xml`, снять теги, сравнить
   заголовки и длину), а не читать все три. Читать ТЗ целиком — противоречия видны только при
   сравнении текста требований с «Приложением: схема БД».
2. **Разобрать примеры данных кодом, а не глазами.** Обязательная программа: кодировка/BOM/
   разделитель/CRLF, форматы дат, колонки, которые есть в данных и отсутствуют в схеме ТЗ, доля
   строк реально по целевой сущности (классифицировать URL/пути регуляркой и посчитать), дубли,
   конфликты, пустые значения, периоды. Это самый информативный источник — реальные выгрузки
   расходятся с ТЗ почти всегда.
3. **Сверить внешние API с документацией, а не с ТЗ.** Лимиты, квоты, срок жизни токена, кто и как
   выдаёт доступ. ТЗ пишут по памяти, цифры в нём протухают, а доступ часто можно получить
   дешевле, чем просит заказчик (гостевой доступ вместо его токена).
4. **Сверить предложенную в ТЗ архитектуру с тем, что уже работает у нас.** Блок «рекомендуемая
   архитектура» написан под исполнителя без инфраструктуры. Если у нас уже есть вход, очередь,
   права, деплой или клиент нужного API — вариант «развернуть всё с нуля / взять BI-инструмент»
   отклонять и перечислять: что переиспользуется, чего нет.
5. **Собрать недоговорённости.** Требование в критериях приёмки без алгоритма — незакрываемый
   пункт. К каждому такому пункту сразу предлагать формулу/правило, а не только вопрос.
6. Ответить разбором (формат ниже) и не начинать код, пока не закрыты два вопроса: доступы и
   недоговорённости.

## Формат разбора

Заказчик, прочитав ТЗ, говорит «не понял суть» — значит нужен разбор, а не пересказ документа.

- **Суть на одном экране**: таблица «шаг → что происходит → откуда данные», одна фраза «по сути
  это …» и один пример реальными числами из примеров данных (статья, визиты, позиция).
- **Что в данных на самом деле**: таблица по файлам с найденными аномалиями и числами («12 из 30
  строк — не статьи журнала»), а не оценками «данные грязные».
- **Где ТЗ противоречит себе или молчит**: нумерованный список, каждый пункт с предлагаемым
  решением.
- **Что переиспользуется** из наших проектов и что придётся писать с нуля (включая отсутствующие
  библиотеки — например, графиков в проекте может не быть вовсе).
- **Что запросить у заказчика** — короткий список, отдельно «чего в архиве нет».
- **Оценка по этапам в днях** с указанием, где оценка ТЗ занижена и почему; отдельно срок
  наблюдения, если приёмка требует «N дней без вмешательства».

Без вступлений, без пересказа ТЗ, без «отличный вопрос».

## Повторная сверка по ходу проекта

Вопрос «что из ТЗ ещё не закрыто?» задаётся регулярно — ответ должен быть проверяемым, а не
пересказом плана.

- **Таблица «блок ТЗ → бэкенд → фронт»**, в каждой ячейке «закрыто / нет» и один факт-доказательство
  (эндпоинт, файл, число строк в БД). Перед ответом каждый пункт сверять с кодом (поиск по имени эндпоинта/модуля/поля),
  а не с roadmap: roadmap отстаёт от кода на несколько шагов.
- **Отдельно назвать блокеры доступа и какой пункт приёмки из-за них недостижим** (нет выгрузки,
  нет токена, нет истории у источника) — это часть ответа, а не оговорка в конце.
- **Вопросы заказчику живут в `local/<проект>/questions.md`** с разделами «уже выяснили сами /
  блокирует приёмку / до фазы N / к эксплуатации». Пункт не удалять после ответа, а закрывать
  ссылкой на проверку («история Topvisor начинается 06.04.2026»). Перед отправкой списка вычищать
  из него то, что проверяется своими запросами: спросить про User-Id, который виден в кабинете и
  нужен любому методу API, — лишний раунд.

## Грабли

- **Образцы данных убеждают, абстракции — нет.** Числа из реальных выгрузок («40% наших URL —
  региональные поддомены, а в схеме ТЗ такой колонки нет») сразу превращаются в решение об
  архитектуре; фраза «данные грязные» — нет.
- **Колонка в данных, которой нет в схеме ТЗ, — всегда сигнал.** Либо ТЗ недописано, либо поле
  появилось позже и на него уже опираются правила (фильтры, алерты). Выписывать такие пары явно.
- **Правила «средняя», «статус растёт/падает», «сезонная поправка» без числового определения** —
  типовые дырки. Предлагать конкретику (не в топе = глубина + 1; порог в процентах; индекс спроса
  по группе), иначе приёмку не закрыть.
- **«История за 2 года» и подобные объёмы проверять на достижимость**: у источников отдача назад
  обычно 90 дней — значит нужен бэкафилл из другого сервиса или пересмотр критерия.
- **Отсутствие кода заказчика — не блокер при наличии форматов.** Оценивать потерю честно (полдня
  на сверку параметров запросов), а не требовать исходники.
- **API-факты и разбор конкретного ТЗ складывать в references навыка проекта**, чтобы в следующей
  сессии не искать квоты заново (образец — аналогичный файл в проекте).
