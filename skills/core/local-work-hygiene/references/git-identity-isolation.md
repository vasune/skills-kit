# Как держать git-личность агента отдельно от владельца

Контекст: одна машина, два аккаунта GitHub — личный у владельца и отдельный аккаунт агента, который он передаёт. Цель: коммиты, ветки, пуши и PR, сделанные агентом, приписываются аккаунту агента, а владелец продолжает работать как сам в тех же репозиториях и не замечает изменений.

## Личность — от чьего имени коммит

Проверено на git 2.54: локальные значения перебивают глобальные и для автора, и для коммиттера, а глобальные значения остаются ровно такими, какими были.

| Ситуация | Настройка |
|---|---|
| В репозитории коммитит только агент | `git config --local user.name "<bot>"` + `git config --local user.email "<bot email>"` |
| В репозитории коммитят и владелец, и агент | переопределение через env на команду, ничего не сохраняется |
| Целое поддерево принадлежит работе агента | `includeIf "gitdir:<path>/"` в глобальном конфиге владельца со ссылкой на отдельный файл личности |

Переопределение на команду — конфиг не тронут, заданы и автор, и коммиттер:

```bash
GIT_AUTHOR_NAME=<bot> GIT_AUTHOR_EMAIL=<bot email> \
GIT_COMMITTER_NAME=<bot> GIT_COMMITTER_EMAIL=<bot email> \
git commit -m "feat: ..."
```

Проверять результат, а не предполагать: `git log -1 --pretty="%an <%ae> | %cn <%ce>"`, и после этого перечитать `git config --global user.name`, чтобы доказать, что конфиг владельца цел.

## Учётные данные — кому разрешено пушить

Личность и учётные данные независимы: коммит с именем бота всё равно пушится тем токеном, который примет remote. Сначала самое чистое:

- **Учётные данные на репозиторий** — `git config --local credential.https://github.com.username <аккаунт-агента>`, а токен агента хранит credential helper для этого хоста. В границах одного репозитория.
- **SSH-ключ на аккаунт + псевдоним хоста** — ключ агента плюс `Host github-agent` / `IdentityFile` в `~/.ssh/config`, remote записываются как `git@github-agent:owner/repo.git`. Ключи не пересекаются, токена в конфиге нет.
- **`gh auth switch`** — переключает, под каким аккаунтом действует CLI `gh` и что настроит `gh auth setup-git`. Удобно для работы с API, но действует на весь хост: перед `gh pr create` и подобным говорить, какой аккаунт активен.

## Как получить авторизацию аккаунта

- Механика device-flow и токенов — в поставляемом навыке `github-auth`: следовать ей там, а не изобретать поток заново.
- Просить scope `workflow` вместе с `repo,read:org,gist`, когда в репозиториях есть файлы GitHub Actions; без него пуш, который трогает `.github/workflows/`, отклоняется.
- Вести поток только для аккаунта, который передал владелец. Не начинать — и не оставлять идущей — авторизацию его личного аккаунта, и никогда не просить токен в чате: пусть он сам впишет его в env-файл агента или введёт код устройства в своём браузере.
- До начала подтвердить, какой аккаунт подключается. Когда намерение — «аккаунт агента, позже», правильное действие — подождать, а не авторизовать тот аккаунт, который сегодня оказался под рукой.
- Владелец может назначить свой аккаунт для коммитов и пушей проекта — обычно потому, что аккаунт агента не состоит в организации, которой принадлежит репозиторий. Делать ровно это, в границах репозитория, и записать в файл рабочего контекста проекта, чтобы следующая сессия не «починила» это обратно на аккаунт агента.

## Разбор: пуш аутентифицируется под чужим аккаунтом

Симптом: `git ls-remote origin` или `git push` падает с `remote: Repository not found` / `fatal: repository ... not found` для приватного репозитория, который заведомо существует, хотя тот же хост нормально отвечает из другого каталога на той же машине. <!-- lang: allow -->

Механизм: `gh auth setup-git` пишет `credential.https://github.com.helper = !<path>/gh auth git-credential` в глобальный конфиг владельца, поэтому git сначала спрашивает аккаунт CLI `gh`. Когда этот аккаунт не состоит в организации-владельце, GitHub отвечает 404 на невидимый приватный репозиторий вместо 403 — ошибка читается как отсутствующий репозиторий, а не как проблема прав. Добавление второго helper на репозиторий этого не лечит: git берёт ПЕРВЫЙ helper, вернувший учётные данные, поэтому helper от gh всё равно выигрывает. Токен назначенного аккаунта должен лежать в хранилище ОС (`osxkeychain` на macOS).

Рецепт (проверено на macOS, git 2.54):

```bash
git config --local --replace-all credential.https://github.com.helper ""
git config --local --add          credential.https://github.com.helper osxkeychain
```

Обе строки важны. Пустое значение helper сбрасывает унаследованный список helper-ов; вторая строка обязана быть `--add`, потому что обычный `git config <ключ> <значение>` заменяет все значения этого ключа и молча выбрасывает строку сброса, возвращая чужой аккаунт вперёд.

Проверить, каким аккаунтом будет пользоваться git, до любого пуша:

```bash
git config --local --get-all credential.https://github.com.helper   # empty line first, then the keystore
printf "protocol=https\nhost=github.com\n\n" | git credential fill | grep '^username='   # must print the designated account
```

`git credential fill` печатает и секрет в stdout — фильтровать до строки с именем пользователя и никогда не вываливать вывод целиком.

Пустой вывод — не отсутствующий репозиторий: `git ls-remote <url>` с кодом 0 и без вывода значит, что remote существует и ссылок в нём пока нет, так что первый `git push -u origin <ветка>` создаст ветку. «Не существует» оставлять для 404. Когда новый remote не отвечает ни так, ни так, проверить учётные данные на репозитории, до которого аккаунт заведомо дотягивается, прежде чем делать выводы о новом.
