# Гигиена локальной работы

Касается любой разовой работы на машине владельца по его просьбе: пробы, эксперименты, прогоны тестов, клоны репозиториев, загрузки, сгенерированные скрипты. Два инварианта: работа остаётся в одном месте, которое владелец видит, а его собственная личность, учётные данные и конфигурация остаются нетронутыми, если он не попросил иначе.

## Когда открывать

Открывать до первого действия задачи, создающего файлы: проба, прогон тестов, `git clone`, скачанный набор данных, одноразовый скрипт. Также открывать при настройке git-личности или учётных данных в репозитории, где работает и сам владелец, и перед любым действием, которое трогает аккаунт провайдера от его имени.

## 1. Артефакты — внутрь рабочего каталога

`<workspace>` — единственное место для такой работы: видимое владельцу место внутри его собственного дерева файлов, которое он назначил при настройке.

Никогда `mktemp`, никогда `/tmp` или `/var/folders`, никогда скрытый черновой каталог агента (этот путь — по документации своего хоста) для работы, о которой владелец попросил. Скрытые пути делают прогон невидимым для него, поэтому даже полностью убранная после себя проба читается как что-то сделанное за спиной. Открытое место ничего не стоит и снимает вопрос целиком.

Стартовая структура — точка отсчёта, а не смирительная рубашка:

Внутри `<workspace>/`:

- `scratch/` — разовые прогоны и черновики (можно удалять целиком)
- `scripts/` — переиспользуемые скрипты
- `reports/` — готовый результат
- `data/` — входные данные и загрузки
- `logs/` — объёмные логи прогонов
- `RUNS.md` — журнал прогонов
- `README.md` — договор с владельцем об этой раскладке; обновлять при каждом изменении структуры, чтобы папка объясняла себя сама, без вопросов

Соседи рабочего каталога, на уровень выше, в `<agent-root>/`:

- `repos/` — рабочие git-клоны (вне `workspace/`, чтобы рабочий каталог оставался расходным)
- `sandbox/` — одноразовые тестовые репозитории и сухие прогоны
- `backup/` — снимки перед шагом, который нельзя отменить: каталоги, которые вот-вот уедут из живого дерева, файл конфигурации, который вот-вот будет правлен. Имя копии — по её сути (`skills-retired-<YYYYMMDD>/`, `config-before-external-dirs.yaml`), чтобы откат был одним `cp -R`, который владелец выполнит, не читая ваш лог

Дробить, переименовывать, вкладывать и добавлять соседние папки в `<agent-root>/` по потребности задачи (мультирепозиторный проект, большой набор данных, долгий поток работы). Держать границу, а не раскладку. Не вводить собственных правил строже, чем просил владелец: жёсткая структура вызывает поправку «не загоняй себя в рамки» — лучше подстроиться.

Собственные проекты владельца живут вне этого дерева, в каталоге его проектов (`<projects>`). Когда он называет это место для клона или форка — типичный случай: разбираем или дорабатываем чужой движок рядом со своими проектами — клон идёт туда, а не в `workspace/` или `repos/`. Рабочий каталог держит прогоны, пробы и разовые данные; папка проектов владельца — то, что он собирается хранить и открывать сам.

**В дереве проектов владельца удалять нечего по своей воле.** Фраза вроде «<тема> из проектов удаляем», сказанная при чистке заметок, означает раздел заметок, а не папку на диске: рабочая копия, клон или репозиторий на GitHub удаляются только по отдельной явной просьбе. Перед любым таким удалением убедиться, что копия запушена (`git fetch -q origin && git rev-parse --short HEAD origin/master`, `git status --porcelain --untracked-files=normal`), и сказать в отчёте, что не вернётся: игнорируемые файлы (`.env`, `node_modules/`, `venv/`, `data/`, `local/`) в git не лежат и клонированием не восстанавливаются.

Ловушки

- На macOS `mktemp -d` уезжает в `/var/folders/…` всякий раз, когда `TMPDIR` не экспортирован в эту оболочку, поэтому «временный каталог» — не безопасное умолчание, даже если окружение объявляет черновой каталог. Передавать путь рабочего каталога явно, а не наследовать его.

## 2. Заметки — в базу знаний, артефакты — сюда

Два разных адреса, и именно их смешение делает файлы владельца нечитаемыми потом:

- **Артефакты** — код, клоны, вывод прогонов, загрузки: `<agent-root>/` как выше. Расходные по замыслу.
- **Знания** — памятки, страницы проектов, инструкции, записи о конфигурации: база знаний в `<kb>/` с её собственным делением на разделы. Инбокса («Входящие») там нет: владелец удалил его как лишний уровень, черновики и сырые выгрузки живут в `<workspace>/`, а в базу попадает уже разобранное. Не заводить раздел по инерции.

В базе есть два файла, которые делают её навигируемой, и оба — часть написания заметки, а не необязательная добавка:

- `README.md` — договор о раскладке. Обновлять при каждом изменении структуры, чтобы папка объясняла себя сама.
- `INDEX.md` — вход в граф: только разделы и служебное, по строке на раздел. Перечень заметок живёт в заметке-разделе своей папки (`Рецепты/Рецепты.md`); заметка, которой нет в нём, не находится. Полного оглавления в корне не держать.

Правила заметок: одна заметка на тему, русское имя файла с заглавной буквы и без даты, а перед созданием файла — поиск по базе: обновлять существующую заметку, а не заводить вторую версию. Секреты в базу не пишутся никогда; указывается, где лежит значение.

Собственный Obsidian-vault владельца (`<vault>`, узнаётся по `.obsidian/`) — его, и он регулярно просит заметки и перестройку именно там (бизнес-модель, конкуренты, план запуска, карты сайта). Правило не «не трогать», а «по просьбе и по его конвенциям»:

- сначала прочитать `README.md` и `INDEX.md` самого vault: граф-дерево (INDEX → заметка-раздел на каждую папку → заметки), одна заметка = одна тема, русское имя файла с заглавной без даты, ссылки `[[...]]` только родитель ↔ дети, даты в формате `ДД.ММ.ГГГГ`;
- новые заметки класть в заметку-раздел своей папки, в `INDEX` попадают только разделы;
- перестройку папок делать только по прямой просьбе и через `git mv`, чтобы история переехала вместе с файлами; перед переносом прогнать `grep -rn '\[\[<старое имя>'` и починить ссылки, иначе граф ломается;
- в конце проверить ссылки машинно: множество `[[целей]]` минус имена файлов должно быть пустым;
- коммитить только когда просят: история vault локальная и никуда не пушится.

## 3. Сначала отчёт, потом уборка

Сказать в ответе: где шло, что создано, что осталось. Для всего, что длилось дольше пары минут или трогало файлы вне рабочего каталога, добавить строку в `RUNS.md` (дата, что, где, результат, остатки). Проверке из одной команды строка в журнале не нужна.

Затем убрать мусор: удалить его или перенести результат в `reports/`. Чистить явным `rm -f <точные пути>`: зачистка деревом через `find … -delete` читается как рекурсивное удаление и отклоняется защитой рантайма сразу, а форма с названными путями работает всегда и легче проверяется. Не оставлять владельцу самому обнаруживать остатки — фраза, которой надо избегать: «я даже не знаю, где ты это делал и что оставил».

Когда владельцу надо действовать вне чата — страница настроек, форма, запрос одноразового кода — записать шаги коротким чек-листом в `reports/` и назвать файл в ответе. Он пройдёт по нему во втором окне, не листая переписку, а тот же файл фиксирует договорённость после его ответа.

Секреты в рабочий каталог не попадают. Токены, ключи и пароли живут только в конфигурационном env-файле агента.

## 4. Личность и учётные данные владельца не трогать

- Глобальный git-конфиг принадлежит владельцу. Не менять его: его имя и почта должны действовать для его собственных коммитов везде.
- Коммитам агента давать ботовскую личность на репозиторий (`git config --local user.name` / `user.email`) или на команду через `GIT_AUTHOR_NAME` / `GIT_AUTHOR_EMAIL` / `GIT_COMMITTER_NAME` / `GIT_COMMITTER_EMAIL`, когда один репозиторий общий и лишь часть коммитов — агентские. Оба способа оставляют `git config --global` нетронутым.
- Коммитить, ветвиться, пушить и открывать PR только под аккаунтом, который владелец явно передал для работы агента. Никогда не авторизовывать его личный аккаунт по своей инициативе, даже если учётные данные доступны и технически сработают, — но исполнять явное указание: когда владелец называет, какой аккаунт коммитит и пушит данный проект (обычная причина — организация, в которой аккаунта агента нет), использовать его, держать переопределение в границах одного этого репозитория и записать договорённость в `local/context.md` проекта.
- Никогда не печатать материал ключа в чат, даже короткий фрагмент, который владелец просит для опознания. Показать маскированную форму и дать однострочную локальную команду, чтобы он сам прочитал хвост.

Проверенные рецепты на репозиторий и на команду, варианты учётных данных для нескольких аккаунтов и разбор пуша, который аутентифицируется под чужим аккаунтом, — в `references/git-identity-isolation.md`.

GitHub-сторона этой передачи — в `github-agent-access`: какие вопросы закрыть до любой авторизации, какие scope просить (минимальные права, никогда «всё»), как проверить учётные данные от начала до конца и что делать, когда токен пришёл через чат.

## 5. Дерево, которым управляет кто-то другой, — только на чтение

Один и тот же каталог проекта может быть живым в другой сессии: делегированные субагенты его собирают, у владельца открыт Xcode или Obsidian на нём, другой агент гоняет тесты. Рабочее дерево общее, поэтому сборка или тест, запущенные, чтобы «проверить состояние», пишут в те же `DerivedData`, `build/`, состояние контейнера и тестовые артефакты, которыми пользуется другой работник: два `xcodebuild` на одном проекте могут заблокировать или испортить вывод друг друга, а цель UI-тестов, глушащая системный звук, при столкновении оставит машину без звука.

Перед любым тяжёлым прогоном в проекте, который создан не в этой сессии, поискать признаки живого хозяина:

```bash
git status --short                              # fresh uncommitted edits = someone is mid-work
ls -lT <dir>/<file>                             # mtime: is it being written right now?
pgrep -fl 'xcodebuild|swift|node|docker|npm'    # is the toolchain already busy?
ls <dir>/local <dir>/docs 2>/dev/null           # session notes like local/context.md often say who owns it
```

Правила:

- Свежие правки с сегодняшней отметкой времени или уже идущая сборка означают: читать и доложить, не собирать, не тестировать, не форматировать. Спросить владельца, чья это работа, прежде чем трогать.
- Если сборка или тест уже прошли в дереве, которое оказалось чужим, сказать об этом одной фразой и перестать трогать репозиторий. Признанное столкновение дешевле молчаливого.
- Статус только на чтение никому не мешает: `git log`, `git status`, `git diff --stat`, `ls`.

## 6. Статус репозитория — это чтение, а не прогон

Когда владелец спрашивает «статус?» про проект, ему нужно состояние, а не проверочный прогон. Набор только на чтение, в таком порядке:

```bash
git rev-parse --abbrev-ref HEAD
git log -8 --format='%h %ad %s' --date=format:'%m-%d %H:%M'
git status --short
git diff --stat
git log origin/master..HEAD --oneline        # unpushed
git rev-list --left-right --count HEAD...origin/master
```

Явно назвать четыре состояния, потому что они и есть ответ: **закоммичено**, **в работе** (незакоммичено, со счётчиком строк), **не запушено** (хеши и количество), **не начато**. Затем отделить проверенное от заявленного: лог тестов с mtime часовой давности проверял состояние, которого больше нет, — писать «проверено сейчас в HH:MM» только про то, что запускал сам, а старые логи помечать их собственной отметкой времени.

- Собирать или тестировать ради ответа на вопрос о статусе только когда дерево свободно и владелец просил проверку; никогда как побочный эффект любопытства.
- Называть блокеры отдельно от прогресса (прогонов не было, документов ещё нет, контейнер лежит, потому что не запущен демон), иначе хорошо подготовленный проект читается как работающий.
- Не подмешивать чужую незакоммиченную работу в свой коммит, чтобы дерево выглядело чистым: перечислить её и спросить.
- **Индексировать по путям, никогда `git add -A`/`git add .`, в дереве с чужими правками.** `git add <точные пути>` — для целых файлов; когда в диффе одного файла смешаны ваша правка и чужая, индексировать только свои хунки: снять `git diff -- <файл>`, оставить заголовок файла и свои блоки `@@`, `git apply --cached --recount <патч>` — остальное остаётся в рабочем дереве, вне индекса и без коммита. Проверять индекс, а не намерение: `git status --short` показывает `MM` для частично проиндексированного файла, `git diff --cached --stat` должен перечислять только те файлы и счётчики строк, которые вы собирались закоммитить, а `git show --stat HEAD` после коммита подтверждает, что ничего лишнего не просочилось.

## 7. Дату брать у машины

Во вложенном контексте «сегодня» может быть устаревшим. Дату брать из `date` и из отметок времени коммитов. Если в репозитории есть коммит с датой позже выданного «сегодня», верить репозиторию, перезапустить `date` и исправить дату в ответе — не подгонять историю под промпт. `git reflog --date=short` показывает переключения, amend и перемещения ветки, чего `git log` по одной ветке не покажет.

Поиск проекта: идти по известным корням, а не обходом домашнего каталога.

```bash
ls -1 <projects> <agent-root>/repos 2>/dev/null
grep -ril "<name>" <kb> | head
```

`find ~/Desktop ~/Documents ~/Developer -maxdepth 4` зависает на папках, защищённых TCC (`~/Documents`, `~/Developer`), и сжигает весь таймаут инструмента — та же защита заставляет поиск по содержимому отклонять эти пути. Назвать корень и оставаться внутри него, иначе проба кончается кодом 124 и без результата.

Ловушка: путь, набранный руками в проект, в котором имя папки содержит пробелы или кириллицу, может разрешиться в *другой* каталог, чем тот, что открыло приложение. Реальный случай: репозиторий, чьё имя содержит дефис, был достигнут через пробел в том же имени; папку переименовали посреди сессии, одна набранная руками запись файла молча создала второй каталог с единственным только что записанным файлом, а настоящий проект остался со старой копией. Перед записью в такой проект собирать путь из листинга (`ls -d <projects>/*<имя>`, `os.listdir` + `os.path.isdir('.git')`), а после записи убедиться, что `git status` в этом каталоге перечисляет файл: файла нет в списке изменённых — значит, запись ушла в другое место. Найденное дублирующее дерево убрать, взяв точное имя из листинга (никогда не перенабирать его).

Ловушка: файл, изменённый скриптом (`python`, массовая перезапись без `sed`, разовый цикл), больше не считается «прочитанным» защитой записи: следующая перезапись отклоняется с сообщением вида «has not seen its full current content» (дословно у разных хостов своё). Одно полное чтение этого пути снимает вопрос; не пытаться обойти защиту через shell-редирект или частичный патч, когда изменение действительно перезапись. <!-- lang: allow -->

Ловушка: удаление каталога, внутри которого сидит рабочий каталог сессии команд, ломает каждую следующую команду этой сессии с «Unable to read current working directory». Сначала выйти оттуда (`cd` в реальный путь) или передать явный рабочий каталог в следующем вызове. То же после `mv` этого каталога: в следующем вызове сделать `cd` заново, а не доверять запомненному сессией пути. <!-- lang: allow -->

Ловушка: обёртка цикла по кускам (`for f in ...; do tool "$f"; done`) и процесс, который она породила, — два процесса. Убийство обёртки оставляет ребёнка работать, а уцелевшая обёртка просто переходит к следующему куску — так «остановленный» прогон продолжается рядом с новым, оба пишут в те же файлы вывода и оба складываются в одни и те же посчитанные по логу тайминги. Убивать обёртку и её ребёнка по явному PID (shell-обёртка может игнорировать `TERM` — поднимать до `-9`), затем дважды перечислить подходящие процессы с промежутком в несколько секунд, прежде чем верить состоянию. `pkill -f <шаблон>` совпадает и с вашей собственной командной строкой, если шаблон в ней есть, поэтому самосовпадение заставляет проверку врать.

Ловушка: разовый Python, который ходит по HTTPS, падает с `CERTIFICATE_VERIFY_FAILED` под интерпретатором с python.org — его установщик не добавляет корневые сертификаты в framework. Писать в загрузке вызов `curl -sL --max-time 25 -A 'Mozilla/5.0' <url>`, а `urllib` держать запасной ветвью, чтобы скрипт работал под любым интерпретатором; пробы на `requests` попадают в ту же ловушку.

Ловушка: долгая работа отслеживается только тогда, когда запущена штатным фоновым способом хоста — с уведомлением о завершении и объектом для опроса (механика — по документации своего хоста). Shell-обёртки (`nohup ... &`, `disown`, `setsid`) штатным способом не считаются, а работа, запущенная в обход него, идёт невидимо: ни уведомления о завершении, ни объекта для опроса. Скорость идущей работы мерить по росту её собственного лога внутри нужного окна, никогда по агрегату, который захватывает период, когда жило больше одной работы.

## 8. Диск: что копится у агента и что можно чистить

«Каталог агента занимает N ГБ, разберись» — сначала инвентарь, потом удаление; карта каталогов конкретного хоста, что в них живёт и какие команды сработали, — по документации своего хоста, класс задачи и правила безопасности — в `references/agent-home-cleanup.md`. Всегдашние правила:

- **Считать с скрытыми каталогами:** `du -sh * .[a-z]*` в каталоге агента — без скрытых из счёта выпадают служебные каталоги (история, бэкапы), а это обычно самые крупные куски.
- **Классифицировать по живости, а не по имени:** смотреть, из какого каталога реально запущены приложение и инструменты. Собранное приложение может быть единственной живой копией, а `build/` и `dist/` рядом — артефактами сборки.
- **Кэш чистить тот, что лежит под каталогом хоста:** у инструментов бывает собственный кэш помимо системного (`uv` и подобные); проверять обе папки, иначе «почистил кэш» освободило не то место.
- **Старые версии инструментов — только по реестру установленного:** каталог версии, которой нет в списке активных, — остаток прошлого обновления. Удалять по имени каталога, а не по «похоже на старое».
- **Окружения инструментов — не мусор:** они пересоздаются сами после удаления, и в отчёте это надо сказать прямо. Выигрыш дают только дубли окружений (две venv разных версий Python в одном каталоге установки).
- **Базу сессий не трогать при живом писателе:** оптимизация откажется, если базу держит гейтвей или приложение (в отказе назван PID). Останавливать их и повторять; принудительный флаг не использовать — это ровно тот случай, из которого получают битую базу.
- **Чужой профиль не чистить** даже когда он выглядит дублем: это отдельная установка владельца. Сказать это в отчёте, чтобы вопрос не возвращался.
- **После чистки — проверить живость хоста:** приложение, гейтвей и модель должны остаться живыми (чем проверять — по документации своего хоста), а в отчёте — что освободилось, что осталось намеренно и что требует действия владельца (например, оптимизация базы при закрытом приложении).
