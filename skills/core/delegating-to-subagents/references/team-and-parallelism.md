# Параллельность

- 4–6 единиц на поток; список файлов у потоков не пересекается.
- Общий контекст дублировать в каждом задании целиком — дети не видят друг друга и не видят родителя.
- **Широкий веер на одном провайдере — источник массовых 429.** Упавшие задачи возвращаются с `HTTP 429 … overloaded`; обычно ошибка приходит до первой правки, поэтому файлы целы. Проверить `git status --short` по путям упавших задач и **добить их самому**: перезапуск всего веера попадает в тот же перегруз, а мелкие правки родитель делает быстрее, чем ждёт ограничения. Переотправлять отдельной делегацией стоит только тяжёлые задачи (десятки килобайт переписи) и по одной.
- Долгие прогоны (сборки, `docker compose build`) — в фоне с уведомлением, а не в синхронном ожидании.



# Долговременные члены команды, а не одноразовые субагенты

Когда работа идёт серией волн, брать **долговременных членов команды**, а не одноразовых субагентов: у члена команды есть адрес, ему можно послать сообщение (курс, стоп, «сдавай отчёт»), его видно в списке с состоянием «работает / не активен», и его можно прервать (конкретные инструменты — по документации своего хоста). Одноразовый субагент при зависании не адресуется: сообщение возвращает «active teammate not found», прекратить его нечем — тик идёт часами, а параллельный поток переписывает те же файлы.

Правила:
- лимит команды — 8 членов; новых не плодить: **переиспользовать неактивных** (один `implementer-backend` на все бэкенд-потоки волны, один `reviewer` на ревью);
- один поток = один член команды = **свой git worktree**; общий каталог на двоих исполнителей — источник гонок (два потока правят одни файлы, «проснувшийся» агент откатывает чужие правки);
- одноразовый `subagent` — только для короткой read-only задачи без последующей координации (разведка, сверка фактов);
- если член команды не отвечает 10–15 минут и не пишет файлов — прервать его, а не ждать: зависший поток дороже потерянной минуты.



# Параллельные агенты в одном репозитории

Несколько детей на одном дереве допустимы, если разведены не только файлы, но и
каталоги сборки — иначе `xcodebuild`/`npm`/`cargo` портят общий build и падают
на чужих артефактах.

- В каждом задании перечислить файлы ребёнка и дать ему личный каталог сборки:
  `-derivedDataPath build-<слаг>`; каталог добавить в `.gitignore` (`build-*/`).
- Генерация проекта (`xcodegen generate`, `npm install`, кодогенерация) —
  эксклюзивная операция: пока один ребёнок её делает, остальные только собираются
  в своих каталогах. Если фича добавляет новые файлы — она идёт последней или
  отдельным потоком.
- Прогон тестов/симулятора отдавать ровно одному ребёнку (или родителю):
  два UI-прогона на одном симуляторе конфликтуют.
- Коммитить самому и **по путям** (`git add <файлы фичи>`), а не `git add -A`: в дереве в этот момент лежит незакоммиченная работа соседнего потока, и её новые (untracked) файлы уезжают в чужой коммит — проверять `git show --stat HEAD` сразу после коммита и при захвате чужих путей не переписывать историю, а честно назвать это в отчёте.
- **В общем дереве ребёнку запрещать `git stash`, `git checkout -- .`, `git reset` и `git worktree`.** `git stash -u` сметает незакоммиченную работу соседа, а `pop` возвращает её не всегда чисто — конфликт оставляет чужие файлы в промежуточном состоянии, и следующий отчёт ребёнка описывает уже не то дерево. Сравнить с базой ему достаточно через `git show HEAD:<путь>` во временный файл; сравнение «старое против нового» делает родитель в отдельном worktree.
- Проверять `git status --short` на отладочные правки детей (стартовая вкладка,
  тестовый флаг, закомментированный код) и вычищать их до коммита.
- Сгенерированные артефакты в `.gitignore` (`.xcodeproj`, lock-файлы, кодогенерация)
  скрывают правки детей от `git status`: после потока, который добавил или удалил
  файлы, регенерируй проект и пересобери сам. Ручной патч сгенерированного файла —
  не результат, он исчезнет при следующей генерации.
- Скриншоты и сборку ребёнка принимать только после собственного прогона:
  у него может быть зелёная сборка в изолированном каталоге при сломанном общем.
- Общий артефакт сборки (docker-контейнер, dev-сервер на общем порту) — эксклюзивная
  операция родителя: ребёнок проверяет на том, что уже поднято, или поднимает своё на
  свободном порту (`--port 5199`), а финальную пересборку родитель делает ОДИН раз после
  всех отчётов. Иначе на общем порту оказывается сборка последнего ребёнка, и правки
  остальных в ней отсутствуют — а каждый ребёнок при этом отчитывается «проверено вживую».
- Если ребёнку всё-таки нужен его сервис на общем стенде — только точечно:
  `docker compose up -d --build --no-deps <сервис>`. Два одновременных `up` без `--no-deps`
  дерутся за имена контейнеров и падают с `Conflict ... name is already in use`; после
  такого падения проверить, что остальные сервисы живы (`docker compose ps`), и не считать
  стенд целым по одному удачному `curl`.
- **Полировочный цикл лечится корректировкой курса, а не ожиданием.** Серия одинаковых пересборок
  (5+ подряд) с косметическими патчами между ними — не прогресс, а уход в перфекционизм:
  отправь корректировку курса: «если ключевые проверки пройдены — сдавай отчёт, косметику
  правим следующим заходом». Перед этим глянуть хвост транскрипта: если в логе осмысленные правки
  по живым замерам — дать доработать, если одна и та же сборка по кругу — остановить.
- Фронт и бэкенд параллельно — только если контракт API зафиксирован в брифинге
  (метод, путь, тело, коды ответов). Контракта нет — сначала ребёнок на бэкенде, потом на
  фронте: вёрстка под придуманный контракт переделывается целиком.
- **Наложение проходок по одному дереву разводится по времени, а не по файлам.** Перестройка
  структуры, фича и чистка комментариев пишут в одни и те же файлы, поэтому порядок фиксированный:
  сначала перенос/структура (меняет пути и импорты), потом фичи на новых путях, последней —
  косметика (комментарии, форматирование). Косметика, отданная параллельно, инвалидирует ссылки
  в брифе соседа (`файл:строка`) и конфликтует на каждом общем файле. Если перестройка и фронт —
  разные деревья (`api/` и `web/`), их можно вести одновременно: контракт HTTP между ними уже
  закоммичен и зафиксирован в обоих брифингах.
- **То же внутри одной стороны: двум потокам нельзя одновременно менять форму общего экспорта**
  (форма конфига, набор полей, имя функции). Даже при непересекающихся файлах один переименует
  `SOURCE_OPTIONS` → `SOURCE_FILTER_OPTIONS`, второй импортирует старое имя, третий поменяет
  форму элемента списка — каждое дерево по отдельности зелёное, а сумма красная. Имена и форму
  контракта прописывать в обоих брифингах дословно либо разводить потоки по очереди.
- **Первый коммит после параллельного потока часто падает на pre-commit — это ожидаемо, а не повод откатывать.**
  Прогнать `tsc` и тесты на всём дереве ДО `git commit`, по ошибкам определить, чей это участок,
  и починить у него; «откатить всё и переделать» теряет чужую готовую работу.
- **Родитель тоже не правит каталог, пока в нём пишет ребёнок.** Соблазн силён: ребёнок делает большую перестройку `web/`, а родитель тем же временем правит «одну мелочь» в соседнем файле. Результат — промежуточный `tsc` светит ошибкой в чужом наполовину готовом файле, ребёнок видит падающие тесты родителя и «поправляет» их под свою новую разметку, а в отчёте появляется строка «эти два теста появились в дереве параллельно». Правило: правки и гейты в этом каталоге — только после отчёта ребёнка; срочная мелочь ждёт или уезжает отдельной задачей ему же.
- **Соседний поток виден ребёнку в `git status` — сказать об этом в брифе.** Двое детей в одном дереве
  (например, чистка комментариев в `api/` и в `web/`) видят чужие изменённые файлы и добросовестно
  пишут в отчёте «в дереве появились правки, которых я не делал» — половина отчёта уходит на
  разбор. Одна строка в `context` («параллельно другой поток правит `<папка>`; его изменения не
  трогать и в отчёте не упоминать») снимает шум и не даёт ребёнку «прибрать» чужое.

- **Гейты прогонять после ВСЕЙ пачки, на общем дереве.** Каждый ребёнок отчитывается зелёным на своём
  срезе, а красное всплывает в пересечении: поток, чистящий комментарии в тестах, и поток,
  переписывающий миграции, по отдельности зелёные, а вместе дают три упавших `test_migration`.
  Поэтому после последнего отчёта — один общий прогон (ruff/pytest/tsc/vitest/слои), и только
  потом коммит; отдельные зелёные отчёты не склеиваются в зелёное дерево.
- **Живую проверку принимать только по идентичности артефакта.** «Проверено на стенде» может
  относиться к старому образу: `docker compose run migrate` берёт существующий образ,
  а `up -d --build` в фоне стартует раньше, чем сборка доедет. Перед проверкой сверять
  `docker compose ps --format '{{.Service}} {{.CreatedAt}}'` (время создания контейнера) и
  `alembic_version`; после правки миграций — явный `docker compose build migrate` перед `run`.
- **Правку навыков/документации проекта отдавать отдельным потоком и вычитывать самому.**
  Ребёнок обновляет факты по своему срезу и оставляет устаревшие соседние (навык продолжал
  утверждать «админ видит журнал всегда» после того, как это правило отменили, и ссылался на
  удалённые номера миграций). Сверять цифры (число тестов, имена файлов) и проверять, что
  каждое утверждение про поведение живо в текущем коде.
