# Брифинг: что обязательно в `context` каждого задания

Ребёнок не видит диалог и не помнит ничего из него — в задании повторять всё:

- путь репозитория и ветку, состояние дерева; список файлов, которые **можно** менять (за его пределами не трогать — проверяется по `git status`);
- образец «делай по образцу `<путь>`» — самый эффективный способ задать форму результата;
- **Число и список — из одного источника.** «Разбери 12 страниц» и перечисленные ниже 13 файлов — расхождение, на которое ребёнок потратит ход и напишет об этом в risks. Длину списка считать скриптом (`len(files)`) и подставлять в бриф это число.
- **Имена файлов не выводить из URL.** Транслитерация и обрезка дают `blog_kak_ustroena_baz.txt` там, где ждёшь `blog/kak-ustroena/`. Давать в брифе путь к индексу (`pages.json`) и правило «найди свой URL в индексе, возьми поле `file`», а не список угаданных имён: иначе ребёнок тратит первые ходы на перебор файлов вместо анализа.
- конкретную команду приёмки, которую он обязан прогнать сам (тест/линт), и требование назвать её вывод в отчёте;
- **формат внешнего API — добытый живым запросом, а не выдуманный.** До брифа сам дёрни ручку одноразовым скриптом и положи в задание дословно: URL, обязательные заголовки, точный синтаксис фильтров/тело и форму ответа (пример JSON). Параметры интеграций не угадываются: значение фильтра без кавычек даёт `400 invalid_parameter`, а без обязательного заголовка приходит `HTTP 200` с телом-ошибкой внутри — ребёнок примет это за пустой результат или начнёт перебирать варианты. Там же фиксируй проверенные факты доступа (номера счётчиков/проектов, сколько записей вернулось) — тогда в брифе будет «фильтр такой, ответ такой» и он не будет изобретать обёртку;
- запрет на личные данные и секреты в коде и тестах;
- запрет коммитить и пушить, если коммит делает родитель.
- **Не совмещать «тесты не трогай» с «все тесты зелёные».** Если приёмочный тест кодирует старую разметку или старый контракт, ребёнок упрётся в противоречие: либо запрет, либо зелёный прогон. В брифинге разделять: «тест не править; если падает из-за смены разметки — назови селектор и строку, решение за мной». Обновлять тест — работа родителя, иначе ребёнок либо тихо подгонит ассерты, либо отчитается «4/4 недостижимо» и остановится.

**Договорённости проекта — отдельным файлом.** Когда работа идёт серией фич, правила (стек, стиль, порядок фич, чего не делать) писать в `docs/AGREEMENTS.md` и просить каждого ребёнка прочитать его первым делом: это дешевле, чем повторять весь брифинг в каждом задании. По требованию пользователя папка `docs/` не попадает в git — держать её в `.gitignore`.

**Правило additive для правок существующего содержимого (главное).** В задании писать дословно: «расширяй; удалять можно только то, что дословно дублирует другие разделы». Без этой фразы ребёнок, которому сказали «пиши только по коду / только то, что подтверждено источником», вычистит всё неподтверждённое — включая схемы, справочные таблицы, списки нормативов и ссылки, перенесённые из первичных файлов заказчика. Это самая дорогая ошибка делегирования: восстановление из `git show HEAD:<файл>` занимает больше времени, чем написание с нуля.

**Не запрещать формат целиком.** «Без ссылок», «без картинок», «без таблиц» ребёнок исполнит буквально и удалит уже существующее. Формулировать как «сохраняй ссылки/картинки, если они уже есть», а в приёмке проверять **инвариант формата**, а не дифф: если ссылки — часть графа (вики-ссылки, оглавление, схема импортов), прогнать проверку графа/сборки. Удалённые ссылки в `git status` выглядят как обычная правка, а ломают достижимость десятков файлов — без прогона проверки это замечают через недели.
