# Версионирование библиотеки навыков в отделный репозиторий

Класс работы: «собери из моих навыков/инструкций/субагентов нормальный
репозиторий». Результат — не копия локальной библиотеки хоста, а курируемый набор
с каталогом, критериями отбора и проверкой целостности.

## 1. Инвентаризация

Размер и вложенность решают, что вообще стоит переносить. Инвентаризация — обход
локальной библиотеки хоста: для каждого `SKILL.md` собрать размер, путь каталога и
состав (`references/`, `scripts/`, `templates/`); каталог библиотеки — в документации своего хоста.

Навык без `references/`, `scripts/`, `templates/` и меньше ~4 КБ — обычно пересказ
общих знаний; его ценность надо доказать отдельно.

## 2. Отбор: три критерия

Артефакт попадает в репозиторий, только если верно всё три:

1. **Из модели не воспроизводится** — внутри свои решения, цифры, гейты, грабли.
2. **Работает в разных проектах** — нет привязки к одному репозиторию/клиенту.
3. **Проверен** — есть след применения (тесты, прогоны), а не «на будущее».

Что отсеивается почти всегда: проектные навыки; обёртки сторонних сервисов
(Notion, Airtable, Box, pdf/docx/xlsx — версионируются апстримом) <!-- lang: allow -->; привязка к
рантайму агента (сессии, cron, DOM приложения); узкие предметные наборы;
личные процессы (учёба, недельные обзоры).

Решение по каждому навыку показывать таблицей с причиной, а не списком
«перенёс вот эти»: пользователь правит выбор, а не переписывает работу.

## 3. Раскладка: группа по смыслу, не по инструменту

```text
skills/<группа>/<навык>/SKILL.md
```

Рабочие группы: `core` (гигиена работы, план, делегирование, мета-навыки),
`architecture`, `code` (TDD, дебаг, ревью, спайк, разведка, QA), `git`, 
`scaffolding`, `delivery`, `docs` (документация, база знаний, отчёты), `security`,
`business`. `git/` объединяет имена, PR и доступ, потому что это одна область.

Два уровня вложенности читают все основные хосты: одни берут категорию из имени
папки, другие раскладывают навыки плоско при установке (кто именно и как —
по документации своего хоста). Плоский список `skills/<навык>` в репо не держать — теряется
смысловая группировка.

Уровень каждого навыка фиксировать в каталоге: **L1** — авторская методология
(правится в репо), **L2** — проверенная общая практика с своими командами и
граблями (можно сжать). Без этой разметки репозиторий «особо важного»
расползается до полной копии библиотеки.

## 4. Перенос и санитайзинг

- Копировать через `shutil.copytree` с игнором `.DS_Store`, `node_modules`,
`sandbox`, `.git`. Мусор в навыке (пустой `sandbox/`) — не переносить.
- Заменить абсолютные пути (`/Users/<name>/…`) на `~` или `<repo>`. Имена
проектов можно оставить как происхождение правил — они и есть ценность навыка;
если репозиторий может стать публичным, спросить и обезличить.
- Старые навыки репозитория, вытесненные полными версиями из библиотеки,
удалять: две версии одного навыка расходятся через неделю. История остаётся в git.
- `related_skills` в frontmatter чистить после копирования: проектные и
несуществующие имена делают ссылки висячими. Фильтр — по множеству имён,
собранному из репозитория целиком (см. следующий пункт).

## 5. Валидатор: две прохода, а не один

Ловушка, которая стоит часа: собрать словарь имён и в том же цикле проверять
`related_skills` — тогда каждая ссылка вперёд («`plan` ещё не встретился»)
репортится как отсутствующая. Двадцать ложных ошибок на живом репозитории.

```python
# 1-й проход: собрать имена и пути
# 2-й проход: frontmatter, ссылки, пути, секреты, INDEX
```

Гейты, которые проверяет `check.py` (дешёвые и все ловят реальное):

- наличие frontmatter, `name` == имя каталога, уникальность имён;
- абсолютные пути `/Users|/home` и шаблоны секретов (`ghp_`, `sk-`, `AKIA`, `BEGIN … PRIVATE KEY`);
- битые относительные ссылки `](…)` (резолвить от каталога файла); перед поиском ссылок вырезать из текста блоки ``` и инлайн-код — иначе документ, где сам синтаксис ссылки цитируется в примере, даёт ложную ошибку;
- полнота `INDEX.md` в обе стороны: навык без строки и строка без навыка;
- мусорные файлы (`.DS_Store`).

**Проверить валидатор на ложное «зелено»**: подложить файл с абсолютным путём,
`sk-…` и битой ссылкой, прогнать, убедиться, что поймал все три, удалить. Без
этого шага «ошибок: 0» ничего не значит.

## 6. Каталог `INDEX.md`

Генерируется из каталогов + рукописных триггеров («когда открывать»), с
`assert set(имён) == set(описанных)`. Колонки: навык, уровень (L1/L2), когда
открывать, доки. В шапке — «на старте пять, остальное по триггеру»: каталог на
37 навыков без этого правила читается как «грузи всё».

## 7. Подключение к агенту

Способ подключения зависит от того, как хост ищет навыки, и это проверяется
пробным навыком, а не выводится из общих соображений. Обход каталога может не
заходить в символические ссылки на каталоги: ссылка на всё дерево даёт ноль
навыков, плоская ссылка на отдельный навык — тоже ноль. «Поставить навыки
ссылкой» в таком хосте — молчаливая установка в пустоту.

Общие правила подключения (точные конфиги, колонки и команды — в документации своего хоста):

- Хост монтирует каталог репозитория строкой в своей конфигурации. Каталог
  читается на месте: правка репозитория видна сразу, копий нет. Вложенные группы
  читаются, категория берётся из имени папки; кириллица в пути не мешает.
- Для куратора и агентских правок такие навыки read-only — правка идёт через git.
- **Порядок разрешения: локальная копия в библиотеке хоста выигрывает.** Внешняя
  копия получает статус перекрытой и в списке не показывается. При переносе из
  библиотеки совпадают все имена, поэтому подключение не меняет ничего, пока
  локальные копии на месте — это надо сказать пользователю до установки, иначе
  он решит, что подключение не работает.
- **Отключение по имени не годится, чтобы спрятать дубль**: фильтр идёт по имени
  после разрешения коллизии, поэтому скрывается и внешняя версия — навык
  исчезает целиком. Локальную копию убирать физически (перенести в бэкап-каталог;
  история остаётся в git).
- Приёмка — список навыков хоста с колонкой происхождения: внешние навыки
  помечены как внешние, проектные, оставшиеся в библиотеке, — как локальные.
- Перед описанием схемы пользователю подложить в `<repo>/skills/<группа>/` навык с
  уникальным именем и убедиться, что он появился с внешним происхождением.
  Проектные навыки (их нет в репозитории) это не затрагивает — они продолжают
  жить в библиотеке.

### Вывод в жизнь: убрать локальные копии

Внешняя версия не работает, пока рядом лежит локальная с тем же именем. Порядок:

1. **Сверить локальное с репозиторием по каждому навыку** (`filecmp` по файлам,
   дифф `SKILL.md` с исключением строк `related_skills`). Пока шла работа,
   фоновый куратор мог дописать в локальные копии новые уроки и `references/` —
   такие правки есть только локально. Влить их в репозиторий (файлы + повторный
   фильтр `related_skills`), закоммитить, и только потом убирать копии.
2. **Перенести каталоги, а не удалить**: `shutil.move` в
   `<agent-root>/backup/skills-retired-<YYYYMMDD>/<категория>/<навык>`,
   сохраняя путь категории; опустевшие категории снять `rmdir`.
3. **Приёмка в цифрах**: число внешних навыков в списке хоста равно числу навыков
   в репозитории; проектные остались локальными; ни одного дубля по имени в
   библиотеке; загрузка любого навыка показывает каталог внутри репозитория
   (команды и названия колонок — в документации своего хоста).
4. **Откат описать сразу**: вернуть бэкап копированием в каталог библиотеки,
   из конфигурации хоста убрать строки подключения. Копия конфигурации снимается
   до его правки.

Для хостов с плоским каталогом (и для произвольного пути) `scripts/install.sh`
раскладывает по каталогу на навык и по умолчанию **копирует**:
ссылки эти инструменты тоже не обязаны обходить, копия работает везде.
`--mode link` остаётся явным флагом с оговоркой в справке; `--force`
перезаписывает уже установленный навык (репозиторий — источник истины), без него
занятый путь печатается конфликтом и не трогается. Произвольный каталог
задаётся абсолютным путём: `--target /path/to/skills`.

**Не устанавливать в живую библиотеку без разрешения**: подключение меняет
порядок разрешения имён для всех совпадающих навыков. Сначала `--dry-run`,
пробный навык и ответ на вопрос «что будет с проектными навыками», потом решение
пользователя.

## 8. Документация сложного навыка

`SKILL.md` — рабочий минимум в контексте. Длинные разборы (правила на несколько
экранов, эталонные структуры) — в `references/<тема>.md` **самого навыка**: файл
едет вместе с навыком при любой установке. Отдельный `docs/` в репозитории не
заводить — при раскладке навыка по плоскому каталогу он не едет, и указатель из
`SKILL.md` становится битым; такой каталог пользователь рано или поздно просит
убрать.

Если тот же текст уже живёт в базе знаний, не переносить его молча: спросить,
какая копия каноническая, и оставить у второй одну строку-указатель. Две
полные копии расходятся через неделю.

## 9. Субагенты и инструкции

`subagents/` — роли (ревьюер, разведчик, писатель документации, исполнитель),
каждая с frontmatter (`name`, `mode: subagent`, `tools`) и телом: что дать в
`context`, что делает, формат ответа, чего не делает. `subagents/README.md` —
бриф делегирования и приёмка (отчёт ребёнка — самоотчёт). Отдельного
`instructions/` в репозитории нет: четыре файла глобальных правил повторяли
навыки (`git-naming`, `test-driven-development`) или пересказывали общее знание
модели, а живое — ведение проекта через `local/` — стало навыком `project-context`.

## 10. Завершение

- Прогнать `check.py`, показать цифры: сколько навыков, L1/L2, объём, ошибок 0.
- Коммит и push — **сам, без спроса**: решение владельца записано в этом навыке
  и в README. Перед коммитом `check.py`, затем коммит по `git-naming`
  и `push origin master`; в ответе — одной строкой, что изменено. Разрешение
  спрашивают только на то, что меняет живую библиотеку навыков.
- Открытые решения перечислить явно: судьба L2, установка в живую библиотеку,
дубль заметки в базе знаний.
