# Определение готовности: постоянная планка проекта

Критерии приёмки отвечают «сделали ли то, что хотели?» и свои у каждой задачи. Определение готовности — одна и та же планка для любой правки, она отвечает «доведено ли до нашего стандарта?». Задача закрыта, только когда выполнены оба.

## Критерии приёмки задачи против постоянной планки

| | Критерии приёмки | Постоянная планка |
|---|---|---|
| Область | одна задача или спека | каждый инкремент |
| Меняется | от задачи к задаче | не меняется, одна на проект |
| Отвечает | «то ли построили?» | «готово ли к жизни?» |
| Владелец | тот, кто планирует задачу | владелец проекта, один раз |
| Пример | «пароль меняется по ссылке из письма» | «тесты зелёные, регрессий нет, документация актуальна» |

## Постоянный чек-лист

Под соло: пункт либо выполнен, либо назван вслух как долг — третьего не дано.

### Корректность
- [ ] Критерии приёмки задачи выполнены.
- [ ] Поведение проверено в работе, а не только сборкой: команда, сценарий, URL.
- [ ] Новое поведение покрыто тестом, который падал без правки; старые тесты зелёные.
- [ ] Обработаны не только удачный путь, но и пустой ввод, ошибка, граница.

### Качество
- [ ] Имена и структура объясняют замысел: комментарий не нужен, чтобы понять «что».
- [ ] Нет дублей логики, мёртвого кода, отладочного вывода и закомментированных блоков.
- [ ] Правка в границах задачи, случайных рефакторингов нет.
- [ ] Линтер и форматтер проходят.

### Интеграция
- [ ] Работает с остальной системой, а не только в изоляции: сквозной сценарий прогнан.
- [ ] Миграции, конфиг и флаги учтены; для публичного интерфейса продумана обратная совместимость.

### Документация
- [ ] Публичные интерфейсы, API и поведение для пользователя описаны.
- [ ] Решение, которое дорого перепридумывать, записано (спека, `ADR`, заметка), и документ описывает текущее состояние, а не историю правки.

### Готовность к выкату
- [ ] Проверены безопасность ввода, доступы и работа с данными.
- [ ] Для новых критичных путей есть лог или метрика.
- [ ] Есть путь отката: как вернуть предыдущее состояние.
- [ ] Человек посмотрел результат до мержа или выката.

## Как применять

- **На задачу** — «Корректность» и «Качество» перед закрытием.
- **На фичу** — плюс «Интеграция» и «Документация».
- **На релиз** — весь чек-лист как пол; деплойные правила добавляет навык деплоя проекта, если он есть в библиотеке.

Настроить под проект один раз и дальше не пересматривать. **Планка, которую пересматривают каждый спринт, — не планка.**

## Красные флаги

- «Готово, только не запускал»: непроверенная работа не готова.
- «Тесты проходят» вместо готовности: документация, регрессии и живой прогон пропущены.
- Планка ниже под дедлайн: одна задача прошла легко, другая — «некогда».
- Критерии приёмки считаются всей планкой: постоянного пола качества нет.
- «Готово» объявлено до того, как человек посмотрел на изменение.
