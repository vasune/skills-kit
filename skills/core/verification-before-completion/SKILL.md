# Доказательство перед заявлением о готовности

Заявление «готово», «исправлено», «проходит», «задеплоено» — это не настроение и не вывод из чтения кода, а факт, который можно воспроизвести командой. Навык ставит между работой и заявлением один шаг: свежий прогон.

## Когда открывать

- Перед любым утверждением о результате: в чате, в отчёте, в коммите, в PR, в итоговом ответе.
- Перед коммитом и пушем — «проверено» должно быть правдой на момент коммита.
- При приёмке отчёта субагента: его отчёт — самоотчёт, а не факт.
- Когда хочется сказать «тесты зелёные», «ошибок нет», «всё работает», «проверил вживую».

## Железный закон

**Нет утверждения без свежего вывода команды в этом же ходе.** Если команда не запускалась сейчас — утверждать нельзя, можно только назвать состояние: «не проверял», «в прошлый раз проходило», «по коду должно работать».

## Гейт: пять шагов

1. **Назвать команду**, которая доказывает именно это утверждение.
2. **Запустить целиком** — не частично, не по памяти, не «тот же тест, что раньше».
3. **Прочитать весь вывод** и код возврата, а не первую строку.
4. **Сверить** вывод с утверждением: совпало — заявлять, не совпало — назвать фактическое состояние.
5. **Только потом заявлять** — вместе с доказательством: команда, ключевые строки, код возврата.

## Заявление → чем доказывается → чем не доказывается

| Заявление | Доказательство | Не доказательство |
|---|---|---|
| Тесты проходят | вывод тестов: 0 failed, exit 0 | прошлый прогон, «должно пройти» |
| Линтер чист | вывод линтера: 0 ошибок, exit 0 | «tsc прошёл», частичный прогон |
| Сборка проходит | exit 0 полной сборки | «лог выглядит нормально» |
| Баг исправлен | тест на исходный симптом: красный до, зелёный после | «код поменял», «причина понятна» |
| Файл записан | `read`/`grep` содержимого с диска | «инструмент ответил успехом» |
| Задеплоено | URL/ID/версия артефакта, проверенные запросом | «команда завершилась без ошибок» |
| Факт об API верен для этой версии | ссылка на документацию именно установленной версии | память модели, пример из другой версии, ответ из блога |
| API принимает мой вызов | ответ реального эндпоинта или пакета этой версии | «сигнатура совпадает», чтение исходников без запуска |
| Субагент сделал | родитель сам прогнал гейты и прочитал дифф | отчёт ребёнка |
| «Стало лучше» | число до и после, способ замера | прилагательное |

## Частые отговорки

Гейт пропускают не от незнания, а от самоуспокоения в момент, когда решение «не запускать» уже принято. Каждая отговорка — мысль, которая должна останавливать, а не разрешать пропуск.

| Мысль | Реальность |
|---|---|
| «Правка тривиальна, ничего не сломает» | Простые правки ломают чаще всего — их не проверяют. У гейта нет исключения по размеру. |
| «CI всё равно поймает» | CI — страховка, а не проверка: срабатывает после пуша, когда правка уже уехала. |
| «Я уверен, что работает» | Уверенность — не доказательство. Назови команду, которая это покажет, и запусти. |
| «Полный прогон слишком долгий» | Тогда запусти сфокусированный — но запусти хоть что-то, свежее. Пропуск целиком не проверяет ничего. |
| «В этой сессии уже запускал» | Раньше ≠ сейчас (см. «Свежесть и полнота»): после каждой правки дерево другое. |

Стоп-фразы — то же самое в момент ускользания: «должно работать теперь», «в этот раз можно», «линтер прошёл» (линтер ≠ тесты ≠ сборка), «агент сказал, что сработало». Поймал такую мысль — остановись и прогони гейт, а не продолжай.

Выход из отговорки один — не обещание «проверю потом», а команда, запущенная сейчас, с выводом и кодом возврата (формат — «Что писать в отчёте»).

## Свежесть и полнота

- **Вывод этого хода, а не прошлого.** После каждой правки — заново: предыдущий зелёный прогон относится к другому дереву.
- **Полный прогон, а не фильтр по выводу.** `grep`/`tail` прячут падения и подменяют код возврата: `cmd | tail` вернёт 0, даже если `cmd` упал. Нужен `set -o pipefail` или `${PIPESTATUS[0]}`.
- **На своём дереве, ветке и артефакте.** Зелёное из соседнего worktree, из старого образа или из чужого отчёта — не доказательство.
- **Числа, а не «зелено».** `424 passed`, `0 failed`, `exit 0`, `4/4` — то, что можно перепроверить.

## Что писать в отчёте

Строка доказательства: `команда → ключевой вывод → код возврата`. Пример: `pytest -q → 424 passed, 0 failed → exit 0`. «0 ошибок» без вывода не считается; «проверено вживую» без URL, скриншота или замера — тоже.

## Где гейт не нужен

- Исследование, оценка, вкус, гипотеза — это не заявления о готовности, доказательство тут другое (источник, замер, цитата).
- Не превращать в ритуал: одна команда на одно утверждение, а не пять на всякий случай.
- **Повторный прогон доказывает, только если код или дерево изменились после прошлого прогона.** Повтор на неизменённом коде — ритуал, а не доказательство: он не добавляет информации к прошлому прогону. После правки — новый прогон; между правками гонять нечего.

## Грабли

- **Зелёный прогон на старом дереве или образе.** Контейнер собран до правки, тесты гонялись до коммита — сверить время/ID артефакта, а не только вывод.
- **Кэш и инкрементальная сборка.** «Собралось» после неудачной правки может означать, что собралось старое: чистая сборка для финального заявления.
- **Одинаковое число тестов у двух параллельных детей** — совпадение, а не подтверждение (см. `delegating-to-subagents`).
- **`git add -A` перед коммитом** без чтения диффа: в коммит уезжает чужая работа.
- **Успех инструмента ≠ результат.** Внешний эффект (деплой, отправка, запись в API) проверяется отдельным запросом.
- **Отчёт субагента как факт.** «Тесты зелёные» из его отчёта не заменяет собственный прогон.
