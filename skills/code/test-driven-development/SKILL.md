# Разработка через тесты (TDD)

## Обзор

Сначала тест. Увидеть, как он падает. Написать минимальный код, чтобы он прошёл.

**Основной принцип:** если вы не видели, как тест падает, вы не знаете, проверяет ли он то, что нужно.

**Нарушать букву правил — значит нарушать их дух.**

## Когда применять

**Всегда:**
- Новые функции
- Исправления багов
- Рефакторинг
- Изменения поведения

**Исключения (сначала спросить владельца):**
- Одноразовые прототипы
- Сгенерированный код
- Файлы конфигурации

Думаете «пропущу TDD только в этот раз»? Стоп. Это рационализация.

## Железный закон

```
NO PRODUCTION CODE WITHOUT A FAILING TEST FIRST
```

Код до теста? Удалить. Начать заново.

**Без исключений:**
- Не оставлять его «как справку»
- Не «адаптировать» его, пока пишете тесты
- Не смотреть на него
- Удалить значит удалить

Писать заново из тестов. Точка.

## Сначала узнать команды репозитория

Цикл один, команды — разные. До первого теста выяснить, как тестирует **этот** репозиторий, и гонять
именно его команды на каждом RED, GREEN и финальной проверке:

- **Чем собирается проект:** `package.json`, `pyproject.toml`, `go.mod`, `Cargo.toml`, `Gemfile`,
  `Makefile`, `Package.swift` или `project.yml` у iOS.
- **Что запускать:** обёртки из репозитория (`./gradlew`, `./mvnw`, `make test`, `npm test`,
  `npx vitest run`, `pytest`, `xcodebuild test`) важнее глобально установленных инструментов.
- **Как прогнать один тест** и как весь набор: это две разные команды, нужны обе.
- **Где живут тесты** и как называются файлы: смотреть соседние, а не изобретать своё.

`pytest` в примерах ниже — образец формы, а не единственный стек. Не предполагать `npm test` по
умолчанию: у Go, Rust, iOS и Python команда своя, и прогон не той команды даёт зелёный отчёт о чужом
коде. Команды, которые гейтят мерж, записаны в README, CONTRIBUTING и CI.

## Цикл RED-GREEN-REFACTOR

### RED — написать падающий тест

Написать один минимальный тест, показывающий, что должно происходить.

**Хороший тест:**
```python
def test_retries_failed_operations_3_times():
    attempts = 0
    def operation():
        nonlocal attempts
        attempts += 1
        if attempts < 3:
            raise Exception('fail')
        return 'success'

    result = retry_operation(operation)

    assert result == 'success'
    assert attempts == 3
```
Чёткое имя, проверяет реальное поведение, одну вещь.

**Плохой тест:**
```python
def test_retry_works():
    mock = MagicMock()
    mock.side_effect = [Exception(), Exception(), 'success']
    result = retry_operation(mock)
    assert result == 'success'  # What about retry count? Timing?
```
Расплывчатое имя, проверяет заглушку, а не настоящий код.

**Требования:**
- Одно поведение на тест
- Чёткое описательное имя (в имени есть «and»? Разделить)
- Настоящий код, а не заглушки (если только это не правда неизбежно) — порядок выбора двойников ниже
- Имя описывает поведение, а не реализацию

### Проверить RED — увидеть, как он падает

**Обязательно. Никогда не пропускать.**

```bash
# Запусти конкретный тест
pytest tests/test_feature.py::test_specific_behavior -v
```

Убедиться:
- Тест падает (а не выдаёт ошибку из опечатки)
- Сообщение о падении ожидаемое
- Падает потому, что функции нет

**Тест прошёл сразу?** Вы проверяете уже существующее поведение. Исправить тест.

**Тест упал с ошибкой?** Исправить ошибку, гонять заново, пока не упадёт правильно.

### GREEN — минимальный код

Написать простейший код, чтобы тест прошёл. Не больше.

**Хорошо:**
```python
def add(a, b):
    return a + b  # Nothing extra
```

**Плохо:**
```python
def add(a, b):
    result = a + b
    logging.info(f"Adding {a} + {b} = {result}")  # Extra!
    return result
```

Не добавлять функции, не рефакторить чужой код и не «улучшать» сверх теста.

**В GREEN жульничать можно:**
- Зашивать возвращаемые значения
- Копипастить
- Дублировать код
- Пропускать граничные случаи

Исправим в REFACTOR.

### Проверить GREEN — увидеть, как он проходит

**Обязательно.**

```bash
# Run the specific test
pytest tests/test_feature.py::test_specific_behavior -v

# Then run ALL tests to check for regressions
pytest tests/ -q
```

Убедиться:
- Тест проходит
- Остальные тесты по-прежнему проходят
- Вывод чистый (без ошибок, предупреждений)

**Тест не прошёл?** Исправить код, а не тест.

**Другие тесты упали?** Чинить регрессии сейчас.

### REFACTOR — уборка

Только после зелёного:
- Убрать дублирование
- Улучшить имена
- Вынести помощники
- Упростить выражения

Держать тесты зелёными всё время. Не добавлять поведение.

**Если тесты упали во время рефакторинга:** откатить сразу. Шагать мельче.

### Повтор

Следующий падающий тест на следующее поведение. По одному циклу за раз.

## Не резать горизонтально

**Не** писать сначала все тесты, а потом всю реализацию. Это горизонтальный разрез: RED превращается в «написать кучу воображаемых тестов», а GREEN — в «заставить кучу пройти». Это даёт хрупкие тесты, потому что тесты проектируются раньше, чем реализация научила вас, какое поведение и какой интерфейс действительно важны.

Вместо этого — вертикальные трассирующие пули:

```text
WRONG:
  RED:   test1, test2, test3, test4
  GREEN: impl1, impl2, impl3, impl4

RIGHT:
  RED→GREEN: test1→impl1
  RED→GREEN: test2→impl2
  RED→GREEN: test3→impl3
```

Трассирующая пуля — один сквозной срез поведения. Он доказывает, что путь работает, учит вас интерфейсу и держит каждый следующий тест на том, что вы только что узнали.

## Сколько каких тестов

Пирамида: ~80 % маленьких, ~15 % средних, ~5 % больших. Пропорция отвечает на вопрос «почему набор
идёт минуты»: если большинство тестов поднимают базу и сеть, падения будут медленными и непонятными,
а флаки — обычным делом.

| Размер | Что можно | Скорость | Пример |
|---|---|---|---|
| Маленький | один процесс, без ввода-вывода, сети и базы | миллисекунды | чистая функция, разбор данных |
| Средний | несколько процессов, только localhost | секунды | API с тестовой базой, компонент |
| Большой | внешние сервисы и машины | минуты | сквозной сценарий, бенчмарк |

Что писать: чистая логика без побочных эффектов — маленький тест; пересечение границы (API, база,
файлы) — средний; критический путь пользователя — большой, и таких мало. **Нравится — поставь на это
тест:** инфраструктура, рефакторинг и миграции не обязаны ловить твои баги, это работа тестов.

## DAMP в тестах

В коде DRY обычно прав. В тестах — DAMP: каждый тест читается как фраза спецификации, без похода в
общую фикстуру, чтобы понять, что он проверяет. Дублирование в тесте допустимо: три строки подготовки,
повторённые трижды, дешевле общей фабрики, из-за которой через месяц неясно, какие данные попали в
проверку.

```python
def test_rejects_empty_title():
    task = create_task(title="", assignee="user-1")
    ...
```

Общая обвязка оправдана, когда собирает предметную сущность целиком (`make_run(status="running")`),
а не прячет по одному параметру. Одна проверка на одно поведение — тоже часть DAMP: тест с пятью
утверждениями непонятно что сломал.

## Двойники: от настоящего к моку

Порядок предпочтения — от самого честного к самому опасному:

1. **Настоящая реализация** — высшее доверие, ловит настоящие баги.
2. **Fake** — работающая замена: база в памяти, тестовый сервер.
3. **Stub** — отдаёт заданные данные, поведения нет.
4. **Mock** — проверяет вызовы; только когда настоящее использовать нельзя.

Мок уместен, если настоящая зависимость медленная, недетерминированная или имеет побочные эффекты,
которые нельзя откатить (внешний платёж, письмо). Мокать всё подряд — получить зелёные тесты при
сломанном проде. **Для краша и отката упражнять настоящую границу:** инъекция исключения — не падение
процесса, а мок транзакции — не откат в базе.

## Почему порядок важен

**«Напишу тесты после, чтобы проверить, что работает»**

Тесты, написанные после кода, проходят сразу. Прошёл сразу — ничего не доказывает:
- Может проверять не то
- Может проверять реализацию, а не поведение
- Может пропустить граничные случаи, о которых вы забыли
- Вы так и не увидели, как он ловит баг

Тест-первым заставляет увидеть падение, доказывая, что тест действительно что-то проверяет.

**«Я уже вручную проверил все граничные случаи»**

Ручное тестирование — разовое. Вам кажется, что проверено всё, но:
- Нет записи, что именно проверялось
- Нельзя перегнать заново, когда код меняется
- Легко забыть случаи под давлением
- «Работало, когда я пробовал» ≠ полнота

Автоматические тесты систематичны. Они идут одинаково каждый раз.

**«Удалять X часов работы — расточительно»**

Ошибка невозвратных затрат. Время уже ушло. Выбор сейчас:
- Удалить и написать заново по TDD (высокая уверенность)
- Оставить и добавить тесты после (низкая уверенность, вероятные баги)

«Расточительство» — это держать код, которому нельзя верить.

**«TDD догматичен, прагматизм — это адаптация»**

TDD И ЕСТЬ прагматизм:
- Находит баги до коммита (быстрее, чем отладка потом)
- Предотвращает регрессии (тесты ловят поломки сразу)
- Документирует поведение (тесты показывают, как пользоваться кодом)
- Даёт возможность рефакторинга (меняй свободно, тесты ловят поломки)

«Прагматичные» сокращения = отладка в проде = медленнее.

**«Тесты после достигают тех же целей — важен дух, а не ритуал»**

Нет. Тесты-после отвечают «что это делает?». Тесты-первыми отвечают «что это должно делать?».

Тесты-после смещены вашей реализацией. Вы проверяете то, что построили, а не то, что требуется. Тесты-первыми заставляют найти граничные случаи до реализации.

## Частые отговорки

| Отговорка | Что на самом деле |
|--------|---------|
| «Слишком просто, чтобы тестировать» | Простой код ломается. Тест занимает 30 секунд. |
| «Протестирую после» | Тест, прошедший сразу, ничего не доказывает. |
| «Тесты после дают те же цели» | Тесты-после = «что это делает?» Тесты-первыми = «что это должно делать?» |
| «Уже проверил вручную» | Разово ≠ систематично. Нет записи, нельзя перегнать. |
| «Удалить X часов — расточительно» | Ошибка невозвратных затрат. Держать непроверенный код — технический долг. |
| «Оставлю как справку, тесты напишу сначала» | Вы к нему адаптируетесь. Это тестирование после. Удалить значит удалить. |
| «Сначала надо исследовать» | Хорошо. Выбросить исследование и начать с TDD. |
| «Тест трудный = дизайн неясен» | Слушать тест. Трудно тестировать = трудно использовать. |
| «TDD меня замедлит» | TDD быстрее отладки. Прагматизм = тест-первым. |
| «Ручной тест быстрее» | Ручной не доказывает граничные случаи. Перепроверять на каждое изменение. |
| «В существующем коде нет тестов» | Вы его улучшаете. Добавлять тесты на код, который трогаете. |

## Красные флаги — СТОП и начать заново

Если поймали себя на любом из этого, удалить код и начать заново по TDD:

- Код до теста
- Тест после реализации
- Тест проходит сразу с первого прогона
- Не можете объяснить, почему тест упал
- Тесты, добавленные «позже»
- Рационализация «только в этот раз»
- «Я уже проверил вручную»
- «Тесты после достигают той же цели»
- «Оставлю как справку» или «адаптирую существующий код»
- «Уже потрачено X часов, удалять расточительно»
- «TDD догматичен, я прагматичен»
- «Здесь другой случай, потому что…»

**Всё это значит: удалить код. Начать заново по TDD.**

## Чек-лист проверки

Перед тем как объявить работу готовой:

- [ ] У каждой новой функции/метода есть тест
- [ ] Видел падение каждого теста до реализации
- [ ] Каждый тест падал по ожидаемой причине (нет функции, а не опечатка)
- [ ] Написан минимальный код, чтобы каждый тест прошёл
- [ ] Все тесты проходят
- [ ] Вывод чистый (без ошибок, предупреждений)
- [ ] Тесты используют настоящий код (заглушки — только если неизбежно)
- [ ] Набор проходит в копии проекта без `.env`, ключей и сети
- [ ] Граничные случаи и ошибки покрыты

Не все пункты отмечены? Вы пропустили TDD. Начать заново.

## Когда застряли

| Проблема | Решение |
|---------|----------|
| Не знаю, как это тестировать | Написать желаемый API. Сначала написать утверждение. Спросить владельца. |
| Тест слишком сложный | Дизайн слишком сложный. Упростить интерфейс. |
| Приходится подменять всё | Код слишком связан. Использовать внедрение зависимостей. |
| Подготовка теста огромная | Вынести помощники. Всё ещё сложно? Упростить дизайн. |

## Как гонять тесты и передавать задачу

### Запуск тестов

Гоняй тесты командой на каждом шаге:

```bash
# RED — убедиться, что тест падает
pytest tests/test_feature.py::test_name -v

# GREEN — убедиться, что тест проходит
pytest tests/test_feature.py::test_name -v

# Полный набор — нет регрессий
pytest tests/ -q
```

### Передача субагенту

Когда отправляете субагентов на реализацию, требование TDD идёт в цель и контекст задачи:

- цель: `Implement [feature] using strict TDD`;
- контекст: шаги навыка (RED → GREEN → рефакторинг), команда тестов проекта, структура файлов;
- доступ: командная строка и файлы репозитория;
- результат: вывод прогонов тестов, а не пересказ.

Имена инструментов, запуск и делегирование различаются по хосту — смотри его документацию.

### С systematic-debugging

Баг найден? Написать падающий тест, воспроизводящий его. Пройти цикл TDD. Тест доказывает исправление и предотвращает регрессию.

Никогда не чинить баги без теста.

## Антипаттерны тестирования

- **Проверка поведения заглушки вместо реального** — заглушки должны проверять взаимодействия, а не заменять тестируемую систему
- **Проверка деталей реализации** — проверять поведение/результаты, а не вызовы внутренних методов
- **Только счастливый путь** — всегда проверять граничные случаи, ошибки и границы
- **Хрупкие тесты** — тесты должны проверять поведение, а не структуру; рефакторинг не должен их ломать
- **Повторный прогон без изменения кода** — после чистого прогона та же команда ничего не доказывает: гонять заново только после правки, а не «на всякий случай»

## Герметичность набора

Зелёный набор, которому нужны ключи, сеть или локальный `.env`, — ложное доказательство: на CI и на
чужой машине он падает там, где код вообще не дошёл до сервиса.

- Тест не должен читать настоящие ключи: подставляй заглушку («пустые поля»), а конфиг — фиктивный.
- Клиенты платных сервисов создавать **лениво** (свойство, а не конструктор): ветка без обращений
  к сервису не требует учётных данных; иначе падает с `Missing credentials` в незадействованном месте.
- Шов под заглушку описывать протоколом (`Protocol` + `@runtime_checkable`), иначе заглушка не проходит
  проверку типов и `isinstance`.
- Проверять явно: прогон в копии проекта **без** `.env` и без переменных окружения (как на CI):
  `rsync -a --exclude .git --exclude .env <проект>/ <песочница>/` и там полный набор тестов.

## Финальное правило

```
Production code → test exists and failed first
Otherwise → not TDD
```

Без исключений без явного разрешения владельца.
