# Именование в Git

Собирает сообщения коммитов вида `[action]: comment` и имена веток `[action]/[what-it-is]` по правилам проекта.

## Когда открывать

Открывать, когда задача — создать коммит в Git, написать сообщение коммита, назвать ветку или разобрать диф и решить, как его закоммитить. Покрывает и новую работу, и переименование уже существующих коммитов.

## Локальные договорённости

- Главная ветка всегда `master` (не `main`).
- Подсказку, которую GitHub показывает после создания репозитория (`git commit -m "first commit"`, `git push -u origin main`), буквально не выполнять: ветка `master`, первый коммит — `chore: initial commit` (если владелец задал свой текст — писать ровно его, см. «Публикация в новый репозиторий»). После первого пуша выставить в репозитории default branch `master` (`gh api -X PATCH repos/<owner>/<repo> -f default_branch=master`): новый репозиторий создаётся с дефолтом `main`, которого в нём нет, и открывается как пустой.
- Настройка окружения коммитится прямо в `master`; всё остальное — через ветку и PR.
- **Ветку проверять до первой правки (`git branch --show-current`), а не после двадцатого коммита.** Задача не про настройку окружения — сразу `feature/*` (или ветка, названная владельцем), иначе серия из десятков коммитов ложится в `master`, и перекладывать её задним числом дорого.
- Если коммиты уже легли в локальный `master` — историю не переписывать: `git branch -f <feature> master`, `git checkout <feature>`, затем `git branch -f master origin/master`. Работа остаётся в feature-ветке, `master` возвращается к состоянию origin, force-push не нужен.
- Агентские коммиты идут от аккаунта, который выдал владелец репозитория.
- **`git commit` фиксирует ВЕСЬ индекс, а не только последний `git add`.** Сделанный раньше `git rm` или `git add` другой темы уезжает в следующий коммит. Перед коммитом — `git status`; удаление чужого файла из индекса — `git restore --staged <путь>` (файл остаётся удалён в дереве, но уходит из коммита).
- **Разъехавшиеся коммиты (ещё не запушенные) переразбиваются, а не подклеиваются:** `git reset --soft HEAD~N`, `git restore --staged .`, затем коммиты по темам; после — `git show --stat --oneline HEAD~2` по каждому, чтобы убедиться, что в нём только его тема. Историю запушенной ветки не переписывать.
- **Запушенный коммит не amend'ить:** `--amend` меняет хеш, push отвечает `non-fast-forward`, а `--force` без просьбы владельца запрещён. Правку оформлять новым коммитом: `git reset --soft origin/<ветка>` (изменения остаются в индексе) → `git commit` → обычный push.
- **Один файл на две темы делится по хункам без интерактивного `add -p`:** разбить `git diff -- <файл>` на патчи (шапка + выбранные `@@`-блоки) и `git apply --cached p1.patch` перед первым коммитом; остаток файла уйдёт во второй через обычный `git add`. Так `SettingsTab` с блоком одной фичи и удалением другого живёт в разных коммитах.
- **Каждый коммит проверять отдельно, а не только HEAD:** `git worktree add /tmp/wt <sha>` → прогон тестов → `git worktree remove --force`. На macOS нет `tac`: перечислять sha явно (`for sha in a1 a2 a3`) и смотреть, что число тестов растёт по ходу ветки; один упавший коммит ломает `bisect`.
  В монорепо с pnpm/npm worktree — дорогой путь: `node_modules` в нём нет, и прогон начинается с установки зависимостей. Если дерево чистое (всё закоммичено), дешевле цикл по месту: `git checkout <sha>` → тесты пакета и сборка затронутого пакета (около 10 с на итерацию) → в конце `git checkout <ветка>`. Перед циклом — `git status --short` пуст, иначе правки владельца уедут в чужой коммит.
- **Автора коммита на GitHub определяет email, а не имя.** `-c user.name=<аккаунт> -c user.email=<чужой email>` даёт коммит от чужого аккаунта: локальный `git log --format='%an'` показывает нужное имя и врёт. Сверять по API: `gh api repos/<owner>/<repo>/pulls/<n>/commits --jq '[.[].author.login] | unique'`. Если автор не тот — переписать только свою ветку: `git filter-branch -f --env-filter 'export GIT_AUTHOR_EMAIL=<верный>; export GIT_COMMITTER_EMAIL=<верный>; export GIT_AUTHOR_NAME=<логин>; export GIT_COMMITTER_NAME=<логин>' master..HEAD`, сверить `git rev-parse HEAD^{tree}` до/после (дерево не меняется) и `git push --force-with-lease` (force — только после явной просьбы владельца).
- **Схлопывание по смыслу без интерактивного rebase:** `git branch backup/<ветка>-before-squash`, затем для каждой группы взять дерево последнего коммита группы и собрать цепочку через `git commit-tree <tree> -p <parent> -m "<msg>"` (скрипт из нескольких строк). Так промежуточные снапшоты остаются теми же, что были в истории, а не пересобранными заново; перед `git reset --hard <новый HEAD>` обязательно `assert "$(git rev-parse HEAD^{tree})" = "$(git rev-parse <new>^{tree})"`. Соседние по времени коммиты одной темы (фича + её правки через один шаг) склеивать можно, только если они идут подряд — иначе нужного дерева просто не существует.

## Безопасность дерева и истории

- Перед правками смотреть состояние дерева (`git status`, `git diff`): в нём могут быть незакоммиченные изменения владельца. Не перезаписывать и не удалять их.
- Разрушительные операции — `reset --hard`, `checkout -- <файл>`, `clean -f`, force-push — только по явной просьбе на каждую. Чужие изменения не прятать в `stash` без разрешения.
- Git-конфиг (`user`, hooks, remotes) без запроса не менять: идентичность настраивается локально (`--local`).
- В коммит попадает только то, что относится к задаче: файлы добавлять явно по именам, а не `git add -A`, если в дереве есть посторонние изменения. Секреты, ключи, локальные конфиги и артефакты сборки — проверять перед коммитом.
- **Скан секретов перед коммитом — по именам файлов, без печати значения.** `git diff --cached -i -G'password|secret|api_key|token' --name-only` перечисляет только имена файлов, в чьём индексированном диффе нашлось совпадение; любой вывод — повод открыть эти файлы и посмотреть глазами. Саму строку с ключом не копировать ни в чат, ни в отчёт, ни в команду: значение, напечатанное один раз, уже утекло в лог вместе с командой.
- Хук отклонил коммит — исправить причину и создать коммит заново; хуки не обходить, чужие коммиты не переделывать.

Ты отвечаешь за сообщения коммитов и имена веток.

## Основной принцип

Действие определять по фактическим изменениям кода, а не по названию задачи, заголовку тикета, формулировке пользователя или имени ветки.

При выборе действия смотреть изменения и диф и определять, что именно изменилось.
Не копировать действие, предложенное пользователем, если фактические изменения указывают на другое действие.

## Публикация в новый репозиторий с чистой историей

Когда проект уезжает в новый (корпоративный) репозиторий и прежнюю историю показывать не надо:

1. Сначала прогнать тесты и линтеры: откатываться на старые коммиты в новом репозитории будет нечем.
2. Внутренние документы и секреты убрать из индекса, оставив на диске: `git rm --cached deploy/deploy.md`, `.env`, `.env.prod`, затем добавить их в `.gitignore`. Проверка: `git ls-files | grep -iE 'deploy\.md|(^|/)\.env'` — пусто.
3. Сохранить историю локальной веткой: `git branch archive/history master`; на GitHub её не пушить.
4. Один коммит без родителей: `git checkout --orphan clean`, `git add -A`, `git commit -m "initial commit"`, `git branch -M clean master`.
5. Пуш и default branch: `git push -u origin master`, затем `gh api -X PATCH repos/<owner>/<repo> -f default_branch=master`.

Текст первого коммита — как попросил владелец: при «initial commit» писать ровно эти два слова без `chore:`; префикс из общего правила — когда формат не задавали. В чужой/существующий репозиторий пушить только после явного согласия, а `--force` — только когда владелец сам просит перезаписать.

### Вариант: новое имя и копия в другой папке

Когда наружу уезжает не та же рабочая копия, а копия проекта под новым именем (демо → боевой репозиторий):

1. Все развилки — одним списком вопросов человеку до первой команды: имя, приватность, история (чистый старт или перенос коммитов), локальная папка, судьба старого репозитория. По одному вопросу в сессии — это лишние круги.
2. Копировать дерево, а не клонировать: `rsync -a --exclude '.git' --exclude 'node_modules' --exclude 'dist' "$SRC/" "$DST/"`. После `git clone` в новом репозитории остался бы старый remote и вся прежняя история.
3. Переименовать самоупоминания: `grep -rn "<старое-имя>"` по проекту, затем `sed -i ''` в `package.json`, `docker-compose.yml` (`image`, `container_name`), README. Иначе имя пакета, образ и контейнер остаются старыми при новом имени репозитория.
4. `.env` и `.env.*` дописать в `.gitignore` с исключением `!.env.example`.
5. Идентичность — `git config --local user.name/user.email` до первого коммита; активный аккаунт сверить `gh auth status`, он должен совпадать с владельцем репозитория.
6. Проверки прогнать в новой папке до коммита (`npm ci`, lint, typecheck, build): откатываться в новом репозитории нечем.
7. `gh repo create <имя> --private --source . --remote origin --push`, затем `gh api -X PATCH repos/<owner>/<repo> -f default_branch=master`.
8. Результат проверять по API, а не по выводу `gh repo create`: `default_branch`, число блобов в `git/trees?recursive=1`, число коммитов, visibility, совпадение `git rev-parse HEAD origin/master`.

- Локальную папку называть по имени репозитория, даже если в обсуждении звучало другое имя-кандидат.
- Старый репозиторий по умолчанию не трогать: архивирование и удаление — только по решению владельца (удаление требует scope `delete_repo` и обычно делается через UI).
- Заметку проекта в базе знаний обновлять в том же проходе: переименовать файл заметки, поправить ссылку в индексной заметке, зафиксировать новый путь, репозиторий и идентичность, оставить упоминание старого репозитория.
- Красный `npm run lint` из-за генерённых компонентов (например `react-refresh/only-export-components` в shadcn-файлах) публикацию не блокирует, но и молчать о нём нельзя: сказать владельцу и предложить правку отдельным коммитом, а не рефакторить сгенерированные файлы по ходу публикации.

Полная последовательность команд — `references/publish-to-new-repo.md`.

# Границы коммита

Коммиты атомарны: один коммит — одна логическая задача или изменение.

Не создавать мега-коммиты, склеивающие несколько независимых задач в один коммит.

Если изменения содержат несколько несвязанных задач, фич, исправлений, рефакторингов, тестов, правок документации или изменений обслуживания, их делят на отдельные коммиты.

У каждого коммита должно быть:

- одна логическая цель
- одно основное изменение
- одно подходящее действие
- один комментарий, описывающий только это изменение

Не объединять несвязанную работу только потому, что она сделана в одно время или лежит в одном рабочем дереве.

Например, это обычно должны быть отдельные коммиты:

```text
feat: add user authentication
test: add authentication tests
docs: update authentication guide
chore: remove unused config
```

Не склеивать их в мега-коммит вроде:

```text
feat: add authentication, tests, docs, and cleanup
```

Если задача естественно требует нескольких связанных правок кода, они могут попасть в один коммит — когда образуют одно цельное логическое изменение.

Цель — не искусственно мелкие коммиты, а фокус каждого коммита на одной логической задаче.

## Размер изменения

Размер — не бюрократия, а предсказуемость ревью и отката. Ориентиры:

- **~100 изменённых строк — норма одного коммита.** Такой коммит читается за один заход и откатывается одной командой.
- **~300 строк — только одна логическая правка.** Если 300 строк набраны из разных тем, это несколько коммитов, а не один.
- **>1000 строк — делить.** Большая правка режется на срезы по ~100 строк: каждый проверяется, коммитится, и только потом начинается следующий.
- **Документация, конфиги и генерация считаются по смыслу, а не по строкам.** 500 строк переформатированного CHANGELOG — один `docs:`-коммит; 30 строк в трёх несвязанных конфигах — три коммита. Строки — ориентир для кода, а не догма.

## Savepoint-цикл

Один проверенный срез — один коммит. Следующий срез начинается только после зелёной проверки предыдущего:

```text
Реализовать срез → прогнать проверки → коммит → следующий срез
```

Если срез не прошёл проверку, возвращаются только свои файлы и только к последнему коммиту:

```bash
git restore <свои-файлы>        # вернуть рабочее дерево к последнему коммиту
git restore --staged <файлы>    # снять свои файлы с индекса, если уже добавил
```

`git reset --hard` для отката среза не использовать: он сносит и чужие незакоммиченные правки, а разрушительные операции у нас — только по явной просьбе на каждую (см. «Безопасность дерева и истории» выше). `git restore .` тоже не годится: точка вернёт всё дерево, включая работу, которая к срезу не относится.

# Сообщения коммитов

Формат строго такой:

```text
[action]: [comment]
```

## Допустимые действия

- feat — добавляет новую функциональность, видимую пользователю
- fix — исправляет неверное или сломанное поведение
- ci — меняет конфигурацию или workflow CI/CD
- refactor — перестраивает код без изменения задуманного поведения
- build — меняет конфигурацию сборки, инструменты сборки или зависимости
- chore — изменения обслуживания, не подходящие под другую категорию
- docs — изменения документации
- test — добавляет или меняет тесты
- style — изменения форматирования или стиля кода без изменения поведения

## Выбор действия

Действие выбирается по основной цели фактических изменений.

Правила приоритета:

1. Исправлено сломанное поведение → fix
2. Добавлена новая функциональность → feat
3. Изменён CI/CD → ci
4. Код перестроен без намеренного изменения поведения → refactor
5. Изменена система сборки или зависимости → build
6. Изменена документация → docs
7. Изменены тесты → test
8. Только форматирование или стиль → style
9. Прочее обслуживание → chore

Если изменение содержит несколько независимых задач, не выбирать одно действие на все. Сначала разделить изменения на отдельные коммиты, затем определить действие для каждого коммита по его фактическим изменениям.

Если несколько изменений — части одной логической задачи, они могут быть представлены одним коммитом. В этом случае выбирается действие, лучше всего отражающее основную цель задачи.

Не ставить feat просто потому, что добавился новый код.

Не ставить refactor, если поведение намеренно изменилось.

Не ставить chore, когда подходит более конкретное действие.

## Комментарий

Комментарий должен:

- быть не длиннее 5–6 слов
- описывать суть изменения
- говорить, что изменилось, а не почему
- быть конкретным
- быть в нижнем регистре
- не заканчиваться точкой
- обходиться без лишних слов
- избегать деталей реализации, если без них можно обойтись

Лучше:

```text
fix: progress bar
```

чем:

```text
fix: fix the progress bar issue
```

Лучше:

```text
feat: add user authentication
```

чем:

```text
feat: implement a completely new authentication system
```

# Имена веток

Формат строго такой:

```text
[action]/[what-it-is]
```

## Допустимые действия

- `feature` — новая функциональность
- `fix` — исправление ошибки
- `refactor` — перестройка кода
- `release` — работа, связанная с релизом
- `docs` — документация
- `test` — тесты

## Выбор действия

Действие ветки определяется целью работы.

- Новая функциональность → `feature`
- Исправление ошибки → `fix`
- Перестройка кода → `refactor`
- Работа над релизом → `release`
- Документация → `docs`
- Тесты → `test`

Действие ветки описывает **цель работы**, а не обязательно итоговое действие коммита.

Ветка может содержать несколько коммитов, но сама ветка должна представлять **одну логическую задачу или кусок работы**.

Не использовать одну ветку для нескольких несвязанных задач, когда их можно разумно разделить.

## Срок жизни ветки

- **Ветка живёт не дольше одного рабочего дня.** За это время она либо вливается, либо явно разбивается на куски.
- **Дольше — делить:** кусок работы режется на ветки по срезам, каждая сливается отдельно. Долгая ветка расходится с `master`, и merge превращается в отдельную задачу с конфликтами.
- **Неизвестно, получится ли вообще, — это `spike`, а не долгая ветка.** Одноразовая проверка гипотезы идёт в отдельной ветке или копии, а её результат — решение, а не полугодовая ветка.

---

## Описание ветки

Часть `[what-it-is]` должна:

- быть в нижнем регистре
- разделять слова дефисами
- не содержать пробелов
- быть краткой
- описывать цель ветки
- обходиться без лишних деталей
- не содержать специфичных для Git префиксов

## Примеры веток

```text
feature/new-ui

feature/user-auth

fix/progress-bar

refactor/api-client

release/v2

docs/installation

test/login-flow
```

# Важное различие

Префиксы коммитов и веток не совпадают.

Коммит:

```text
feat: add user authentication
```

Ветка:

```text
feature/user-auth
```

Коммит:

```text
fix: progress bar
```

Ветка:

```text
fix/progress-bar
```

Коммит:

```text
refactor: simplify api client
```

Ветка:

```text
refactor/api-client
```

# Проверка

Перед выдачей сообщения коммита или имени ветки проверить его по правилам.

### Проверка коммита

- [ ] Используется допустимое действие
- [ ] Формат — действие, двоеточие, комментарий
- [ ] Комментарий не длиннее 5–6 слов
- [ ] Комментарий в нижнем регистре
- [ ] Комментарий описывает фактическое изменение
- [ ] Без лишних объяснений
- [ ] Без точки в конце
- [ ] Представляет одну логическую задачу
- [ ] Не склеивает несвязанные изменения в мега-коммит

### Проверка ветки

- [ ] Используется допустимое действие
- [ ] Формат — действие, слэш, описание
- [ ] Описание в нижнем регистре
- [ ] Слова разделены дефисами
- [ ] Описание краткое
- [ ] Описание отражает фактическую цель
- [ ] Представляет один логический кусок работы

Если сгенерированное имя нарушает хоть одно правило — переделать его до выдачи.

# Вывод

Когда пользователь просит сообщение коммита, возвращать только сообщение коммита, если дополнительное объяснение не запрошено явно.

Когда пользователь просит имя ветки, возвращать только имя ветки, если дополнительное объяснение не запрошено явно.

Когда пользователь просит и то и другое, возвращать:

```text
Commit: <commit message>

Branch: <branch name>
```
