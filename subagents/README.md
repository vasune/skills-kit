# Субагенты

Роли для делегирования. Файл роли — это не прошивка рантайма, а бриф: что
ребёнку дают, что он делает, в каком виде возвращает и чего не имеет права
трогать. Одинаково читается человеком и подставляется в `context` задания при
передаче задачи субагенту (в разных хостах называется по-разному).

Полная механика делегирования — навык
[`core/delegating-to-subagents`](../skills/core/delegating-to-subagents/SKILL.md);
здесь то, что нужно помнить перед каждым запуском.

## Роли

| Файл | Роль | Права | Когда |
|---|---|---|---|
| [`code-reviewer.md`](code-reviewer.md) | ревью диффа, PR, недавних правок | read-only | перед merge или коммитом |
| [`security-auditor.md`](security-auditor.md) | прицельный security-аудит: границы доверия, PoC, severity | read-only | перед выкатом или при подозрении на уязвимость |
| [`codebase-scout.md`](codebase-scout.md) | разведка незнакомого кода | read-only | до правок в чужом проекте |
| [`doc-writer.md`](doc-writer.md) | документация проекта в базу знаний | write в свой раздел заметок | проект оброс решениями |
| [`implementer.md`](implementer.md) | ограниченный набор файлов по образцу | write в перечисленные файлы | задача распадается на независимые куски |

## Что делегировать

| Ситуация | Решение |
|---|---|
| Один артефакт: дифф, карта кода, документ, кусок работы | одна роль — та, чей это артефакт |
| Независимые подзадачи без общих файлов | fan-out: 4–6 ролей параллельно, у каждой своя приёмка |
| Зависимые шаги: результат одного нужен другому | последовательно, отчёт шага 1 идёт в `context` шага 2 |
| Ревью и прицельный security-аудит одного диффа | две роли параллельно: `code-reviewer` + `security-auditor` |

**Персона не вызывает персону.** Ребёнок не запускает детей и не передаёт задачу
дальше: нужна другая роль — это рекомендация в отчёте, а оркестрирует родитель.
Так нет рекурсии и двойного счёта токенов.

## Бриф: что обязано быть в `context`

Дети не видят ни диалог, ни друг друга — всё нужное передаётся явно.

1. **Место.** Путь репозитория, ветка, состояние дерева (`git status --short`),
   список файлов, которые **можно** менять.
2. **Образец.** «Делай по образцу `<путь>`» — самый быстрый способ задать форму
   кода, документа или ответа.
3. **Приёмка.** Команда, которую ребёнок обязан прогнать сам, и требование
   привести её вывод дословно. Без команды приёмки задание не выдаётся.
4. **Запреты.** Чужие файлы, `git stash` / `reset` / `checkout -- .`, коммиты и
   push, секреты и личные данные в коде и в выводе.
5. **Язык и стиль ответа.** Иначе ребёнок принесёт свой.

## Приёмка результата

Отчёт ребёнка — самоотчёт, а не факт. Родитель проверяет сам:

1. `git status --short -uall` — тронуты только разрешённые файлы.
2. Диф против `git show HEAD:<файл>` — не переписан ли файл мимо задачи.
3. 3–5 утверждений из отчёта сверить с кодом глазами.
4. Гейты (тесты, линт, типы, сборка) прогнать самому, не верить слову «зелёные».
5. Живой результат посмотреть: страница, окно, отчёт — не «должно работать».

Числа вместо «стало лучше»: тесты до/после, число файлов, байты, замеры.
«Готово» без чисел — не готово.

## Границы

- 4–6 потоков, непересекающиеся файлы и каталоги сборки.
- Общий артефакт (стенд, контейнер, dev-сервер) держит только родитель.
- Архитектура, вкус и приоритеты решаются до делегации: ребёнок спросить не
  умеет.
- Merge и push — только человек, по прямой просьбе.
